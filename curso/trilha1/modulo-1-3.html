📝 /commit - Smart AI-Powered Commits

The command/commitanalyzes all staged changes in git, understands thesemantic purpose of the changesand generates a clear, structured, and informative commit message - all automatically. The era of commits like "fix stuff" or "update files" is over.

Main Concept

🎯Main Concept

When you run /commit, Claude Code does agit diff --stagedinternal, analyzes each change and generates a message followingConventional Commitments(feat, fix, refactor, docs, etc). You approve, edit or reject before confirming.

  • • Semantic analysis:Claude doesn't just look at the modified files - he understands what the change does. Renaming a variable generates "refactor:", fixing a bug generates "fix:", adding functionality generates "feat:"
  • • Structured message:Concise title on the first line (max 72 characters), explanatory body with context, and optionally list of affected files
  • • Mandatory approval:Claude shows the proposed message and waits for your OK. You can accept, edit manually or ask to regenerate with different instructions
  • • Git add automatically:If you haven't staged the changes, Claude asks if it should be added automatically. It shows which files will be included
Code Example

💻Example in Terminal

> /commit
# Claude analyzes the diff and proposes:
Proposed commit message:
feat(auth): add JWT refresh token rotation
Implement automatic refresh token rotation on each
token refresh request. Old refresh tokens are
invalidated immediately to prevent replay attacks.
Files changed: auth/tokens.ts, auth/middleware.ts
# [Y]es / [N]o / [E]dit?
Practical Tip

💡Practical Tip

For best results, make commitsatomic- small commits focused on a single change. If you modified 15 files for 3 different tasks, /commit will generate a generic message. Prefer to make 3 separate commits.

You can also give extra context:/commit isso corrige o bug #142 do Jiraand Claude will include the reference in the message.

🔍 /review - Automated code review

O /reviewmakes Claude Code analyze pending changes in your repository as if it were asenior code reviewer. It identifies potential bugs, security issues, standards violations and suggests improvements - all before you open the PR.

Main Concept

🎯Main Concept

/review examines the diff of uncommitted changes (or the last commit, depending on the context) and generates astructured review reportwith severity categories, explanations and correction suggestions.

  • • Severity levels:Each issue found and classified as Critical (serious bugs, vulnerabilities), Warning (potential problems, code smells) or Suggestion (optional improvements, style)
  • • Full context:Claude doesn't just analyze the isolated diff - he reads the related files to understand if the change is consistent with the rest of the codebase
  • • Analysis categories:Logical bugs, security vulnerabilities, performance, error handling, typing, naming conventions and missing documentation
  • • Actionable suggestions:Each issue comes with a concrete suggestion on how to fix it, including code snippets where relevant.
Code Example

💻Example of /review output

> /review
# Typical result:
CRITICAL (1):
- auth/tokens.ts:45 - SQL injection vulnerability
in user query parameter. Use parameterized query.
WARNING (2):
- api/routes.ts:23 - Missing error handling for
async database call. Add try/catch block.
- utils/cache.ts:67 - Hardcoded TTL cache. Consider
extracting to environmental variables.
SUGGESTION (1):
- api/routes.ts:15 - Consider extracting route
handlers to separate controller files.
Practical Tip

💡Practical Tip

Rotate/review before each /commit. And how to have a reviewer available 24/7 who never complains about being called at 3 in the morning. Fixing problems before commit is infinitely cheaper than fixing them after deployment.

For more targeted reviews, add context:/review foque em seguranca e performanceand Claude will prioritize these categories in the analysis.

🔀 /pr - Complete pull requests

O /prCreates a complete pull request on GitHub (or GitLab) directly from the terminal. Claude analyzes all commits in the branch, generates adescriptive title and a detailed bodywith summary of changes, motivation and testing instructions.

Main Concept

🎯Main Concept

/pr uses the GitHub CLI (gh) under the covers. It analyzes thecomplete diff between your branch and main, understands the global purpose of the changes and generates professional PR that facilitates the work of reviewers.

  • • Clever title:Automatically generated from the change set, following project conventions. Short, clear and descriptive
  • • Structured body:Includes summary of changes, motivation/context, list of modified files, and testing instructions where relevant
  • • GitHub Integration:Requires theghCLI installed and authenticated. The PR is created directly in the remote repository
  • • Pre-PR Review:Claude automatically does a /review before creating the PR, warning you if there are problems that should be fixed first
Code Example

💻Example in Terminal

> /pr
# Claude analyzes all the commits in the branch and proposes:
Creating PR: feat(auth): implement JWT refresh token rotation
Base branch: main
Commits: 3
Files changed: 5
PR body preview:
## Summary
Adds automatic refresh token rotation...
##Changes
- New TokenRotation service in auth/tokens.ts
- Updated auth middleware to handle rotation
- Added migration for token_family column
# Create PR? [Y]es / [N]o / [E]dit
Practical Tip

💡Practical Tip

Before using /pr, make sure theghCLI is installed and authenticated (gh auth status). Without it, Claude cannot create the PR on GitHub.

For PRs with additional context, use:/pr esta mudanca resolve o issue #42 e precisa de review de seguranca. Claude will include this information in the body of the PR and link the issue automatically.

🏗️ /init - Generating CLAUDE.md automatically

O /initand the command that automatically generates the fileCLAUDE.md- the "instruction manual" that Claude Code reads at the beginning of each session to understand his project. It's the starting point for customizing how Claude interacts with your codebase.

Main Concept

🎯Main Concept

/init scans your entire project - folder structure, package.json, settings, README, tests - and generates a CLAUDE.mdtailor-madewhich describes the project, its conventions, useful commands and rules that Claude must follow.

  • • Automatic scan:Claude reads the project structure, identifies frameworks (React, Next.js, Django, Rails), detects lint, test and build tools, and generates instructions based on what it finds
  • • Content generated:Project description, technology stack, development commands (build, test, lint), code conventions and commit patterns
  • • Editable file:The generated CLAUDE.md is a starting point. You must edit it to add specific rules, team preferences, and information that the scan does not capture
  • • Impact on the session:Every time you open Claude Code in a folder with CLAUDE.md, it reads this file first. And how to give Claude a briefing before starting work
Code Example

💻Example in Terminal

> /init
# Claude scans the project and generates:
Scanning project structure...
Detected: Next.js 14 + TypeScript + Prisma + Tailwind
Found: 23 source files, 12 test files, 3 config files
Generated CLAUDE.md with:
- Project description
- Tech stack details
- Development commands
- Code conventions
- Architecture overview
Created: ./CLAUDE.md (47 lines)
Practical Tip

💡Practical Tip

Rotate/initonce to generate the base, thenedit manuallyto add critical rules like: "never delete migrations", "use Zustand instead of Redux", "tests must cover at least 80%". The automatically generated CLAUDE.md is good, but the one edited by you is excellent.

You will learn everything about CLAUDE.md in Track 2 of this course. /init is the entry point.

🩺 /doctor - Problem diagnosis

O /doctorand the Claude Code troubleshooting command. When something doesn't work as expected - an MCP won't connect, permissions are wrong or the environment is misconfigured - /doctordiagnoses and suggests the solution.

Main Concept

🎯Main Concept

/doctor runs a series ofautomatic checksin the environment: checks authentication, tests MCP connections, validates configurations and identifies conflicts. It's like a complete "check-up" of your Claude Code installation.

  • • Authentication:Checks if the access token is valid, if the account is active and if the plan supports the features you are trying to use
  • • MCP servers:Test each configured MCP: is it running? Respond? Are the tools accessible? If any MCP failed, it shows the specific error
  • • Settings:Validates settings.json, CLAUDE.md and project permissions. Points out conflicts such as blocked tools that you are trying to use
  • • Environment:Check Node.js version, Claude Code version, git version, and whether auxiliary tools like gh CLI are available
Code Example

💻Example in Terminal

> /doctor
# Typical check:
✓ Authentication: Valid (Pro Plan)
✓ Claude Code version: 1.0.34 (latest)
✓ Node.js: v20.11.0
✓ Git: 2.43.0
✓ gh CLI: 2.45.0 (authenticated)
✓ MCP: filesystem - connected (4 tools)
✓ MCP: github - connected (12 tools)
✗ MCP: postgres - connection refused
→ Check if PostgreSQL is running on port 5432
→ Verify connection string in .env
✓ CLAUDE.md: Found (47 lines)
Practical Tip

💡Practical Tip

Whenever you encounter unexpected behavior, the first thing to do is run/doctor. In 80% of cases, the problem is a disconnected MCP or a misconfiguration that /doctor identifies within seconds.

Rotate/doctoralso after updating Claude Code or after installing new MCPs. It's the quickest way to confirm that everything is working correctly.

🔄 Complete flow: from code to PR

Now that you know each command individually, let's assemble thecomplete workflowwhich leads from the written code to the pull request opened on GitHub. This is the flow that professional developers use daily with Claude Code.

Main Concept

🎯Main Concept

The complete delivery cycle with Claude Code follows a logical sequence:code → review → commit → PR. Each slash command fits perfectly into this pipeline, forming a continuous flow from the terminal to GitHub.

  • • Step 1 - Develop:Ask Claude to implement the feature or fix the bug. It edits the necessary files with visual diffs for your approval
  • • Step 2 - /review:Review changes before committing. Correct any critical issue or relevant warning identified by the review
  • • Step 3 - /commit:Generate a commit with a semantic message. For large changes, make atomic commits per feature
  • • Step 4 - /pr:Create the pull request with full description. Claude includes everything a reviewer needs to evaluate the PR
Complete Workflow Example

💻Complete Workflow in the Terminal

# 1. Implement the feature
> Add email validation to the registration form
# 2. Review changes
> /review
# 3. Fix issues found (if any)
> Correct the warnings highlighted in the review
#4. Commit with Smart Message
> /commit
# 5. Create the pull request
> /pr
Do vs Avoid

✓ What TO DO

  • ✓ Always run /review before /commit
  • ✓ Fix critical issues before committing
  • ✓ Read the commit message before approving

✗ What NOT to do

  • ✗ Skip /review and commit directly
  • ✗ Make giant commits with 20+ changed files
  • ✗ Create PR without checking if the tests pass
Practical Tip

💡Practical Tip

The /review → /commit → /pr workflow can be executed in less than2 minutes. Compare with the manual process: writing commit message, opening the browser, creating the PR, writing the description, adding reviewers. Claude Code automates all of this.

For projects with CI/CD, /pr can also check whether the checks passed before creating the pull request, avoiding PRs with broken pipelines.
