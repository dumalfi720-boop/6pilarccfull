🔍 Identifying coverage gaps

Before writing tests, you need to knowwhat to test. Claude Code can analyze your source code, identify uncovered functions, untested paths and exposed critical logic. This initial analysis is what separates useful tests from tests that just inflate metrics.

Main Concept

🎯Main Concept

Claude can read your coverage report (lcov, istanbul, pytest-cov) and cross-reference the source code to identify exactly which functions, branches and lines are not covered. More than that, he prioritizesrisk of what is not tested.

  • • Coverage analysis:Ask Claude to read the coverage report and list the functions with 0% coverage, prioritizing the most critical ones
  • • Branches discovered:Identify if/else, try/catch and switch/case that only have one tested path - these are the biggest blind spots
  • • Prioritization by risk:Functions that deal with money, authentication, sensitive data or external integration should be tested first
  • • Effective prompt: "Analise a cobertura de testes deste projeto. Identifique as 10 funcoes mais criticas sem testes."
Code Example

💻Example in Terminal

# Generate coverage report first
$ npm test -- --coverage
# Ask Claude to analyze
> Read the coverage report at coverage/lcov-report/index.html and identify the most critical untested functions. Prioritize by business risk.
Practical Tip

💡Practical Tip

Don't blindly seek 100% coverage. Ask Claude to focus on the20% of the code that represents 80% of the risk: payment functions, authentication, data validation and core business logic.

A good approach is to say: "Given that we have 40% coverage, what functions should I test to have the greatest impact on system reliability?"

✍️ Generating tests with Claude

With the gaps identified, and time togenerate comprehensive tests. Claude Code reads the function's source code, understands its expected behavior, identifies edge cases and generates complete tests that follow your project's conventions.

Main Concept

🎯Main Concept

Claude generates tests that cover thehappy path, expected errors and edge cases. It analyzes the function signature, input/output types, dependencies, and business context to create meaningful tests.

  • • Full tests:Claude generates tests for happy path, error cases, boundary values ​​and null/undefined inputs automatically
  • • Project conventions:If you already have existing tests, Claude imitates the style (describe/it, test(), assert vs expect) and folder structure
  • • Smart Mocks:Claude identifies external dependencies (database, APIs, filesystem) and generates appropriate mocks
  • • Effective prompt: "Escreva testes para a funcao calculateDiscount em src/pricing.ts. Cubra happy path, erros e edge cases. Use o mesmo estilo dos testes existentes."
Code Example

💻Example in Terminal

# Comprehensive test generation
> Read src/services/auth.ts and write complete unit tests. Include:
- Login with valid credentials
- Login with wrong password
- Non-existent user
- Expired token
- Rate limiting
Follow the test pattern in __tests__/
Practical Tip

💡Practical Tip

Always ask Claude to read existing tests before generating new ones. This ensures style consistency. Use:"Leia os testes existentes em __tests__/ para entender o padrao, depois gere testes para X."

For complex functions, ask for testing in stages: first the happy path, then the errors, then the edge cases. This gives more detailed results than asking for everything at once.

3

▶️ Checking and running tests

AI-generated tests need to bevalidated and executed. Claude Code can run the tests, interpret failures, correct the test code and re-run until they all pass. This feedback loop is one of Claude's biggest advantages over traditional test generators.

Main Concept

🎯Main Concept

The validation workflow is iterative:generates → runs → fails → corrects → runs again. Claude understands error messages, stack traces and diffs to adjust tests until they are correct. This is done in a natural conversational loop.

  • • Run tests:Ask Claude to runnpm test ou pytestand analyze the results automatically
  • • Interpret faults:Claude reads the error output and distinguishes between poorly written tests (fixes the test) and real bugs in the code (reports the bug)
  • • Automatic fix:When the test fails due to incorrect setup (wrong mock, missing import), Claude corrects it and re-executes it
  • • Bug discovery:Failed tests can reveal real bugs in production code - Claude distinguishes between the two scenarios
Code Example

💻Example in Terminal

# Ask to run and correct
> Run the tests you just created. If one fails, analyze the error and correct it. Repeat until everyone passes.
# Typical result:
Running: npm test -- --testPathPattern=auth.test.ts
FAIL: 2 out of 8 tests failed
Correcting database mock...
Running again...
PASS: 8 out of 8 tests passed
Practical Tip

💡Practical Tip

Instruct Claude to make no more than 3 correction attempts per test. If a test fails 3 times, there is probably a design problem that needs human intervention.

Add to CLAUDE.md:"Apos gerar testes, sempre rode-os. Se falharem, corrija e rode novamente. Maximo 3 tentativas por teste."

4

📈 Coverage check (measuring improvement)

After generating and validating the tests, it is time tomeasure the real impact. Claude can run the coverage report before and after, calculate the improvement and identify what is still missing to reach the desired coverage goal.

Main Concept

🎯Main Concept

Coverage check and thequantitative feedbackof your testing effort. Claude compares the before and after, shows the evolution by file/function and suggests next steps to continue improving coverage in a strategic way.

  • • Before vs after:Run coverage before generating tests and after. Claude calculates the delta and shows which areas have improved
  • • Important metrics:Line coverage, branch coverage and function coverage. Branch coverage is the most revealing - it shows whether all logical paths are tested
  • • Remaining gaps:Claude identifies what is still missing and estimates how many additional tests are needed to reach the goal
  • • CI integration:Configure a minimum threshold in CI (e.g. 80%) and Claude helps you maintain this goal in each PR
Code Example

💻Example in Terminal

# Check coverage after new tests
> Run npm test -- --coverage and compare with the previous coverage. Show the evolution per file and suggest next steps to reach 80%.
# Typical result:
Coverage before: 42.3%
Coverage after: 67.8% (+25.5%)
Missing: auth.ts (branch 60%), payment.ts (0%), utils.ts (line 45-67)
Practical Tip

💡Practical Tip

Don't chase 100% coverage - the return drops dramatically after 80%. The effort to go from 80% to 90% is often greater than from 40% to 80%. Focus on branch coverage for critical logic.

Create a script in package.json:"test:coverage": "jest --coverage --coverageThreshold='{\"global\":{\"branches\":80}}'"to set the threshold automatically.

5

🔴🟢 TDD with Claude Code (test-first)

Claude Code is an ideal partner forTest-Driven Development. You describe the desired behavior, Claude writes the test first (which fails), then implements the code to make the test pass. The Red-Green-Refactor cycle gains extraordinary speed.

Main Concept

🎯Main Concept

In TDD assisted by Claude, the cycle is:describe the behavior → Claude writes the test → test fails (RED) → Claude implements the code → test passes (GREEN) → Claude refactors (REFACTOR). You conduct the specification, Claude executes it.

  • • RED - Write the test:Describe the behavior in natural language and ask Claude to write just the test (no implementation)
  • • GREEN - Implement:Ask Claude to implement the minimum code necessary for the test to pass
  • • REFACTOR - Improve:With the green test as a safety net, ask Claude to refactor the code while keeping the tests passing
  • • Fast iteration:Claude does the complete cycle in minutes, where it would take hours manually. You focus on the specification, he focuses on the implementation
Code Example

💻Example in Terminal

# Step 1: RED - Write the test
> Write a test for a calculateShipping function that:
- Free shipping returns for orders over R$200
- Charges R$15 for orders between R$100 and R$200
- Charges R$25 for orders under R$100
DO NOT implement the function, just test it.
# Step 2: GREEN - Implement
> Now implement the calculateShipping function to make all tests pass.
# Step 3: REFACTOR
> Refactor the implementation to be more readable while keeping the tests green.
Practical Tip

💡Practical Tip

TDD with Claude works best when you describe behaviors rather than implementations. Say "free shipping must be returned for orders over R$200" instead of "use an if to check if the value is greater than 200".

Add to CLAUDE.md:"Quando eu disser 'TDD', escreva primeiro os testes, depois implemente o codigo para passar os testes, e finalmente refatore."

6

🧊 Edge case testing

The most dangerous bugs live inedge cases: limit values, unexpected inputs, race conditions and impossible states. Claude Code is excellent at thinking about these scenarios that humans often forget, generating tests that cover boundary values ​​and error paths.

Main Concept

🎯Main Concept

Edge cases are scenarios that lie on the edges of expected behavior. Claude can analyze a function and systematically generate tests tonull values, empty lists, negative numbers, giant strings, special characters, wrong types and concurrent states.

  • • Boundary values:Values ​​at the exact limit (0, -1, MAX_INT, empty string, array with 1 element) are where most bugs hide
  • • Error paths:What happens when the API returns 500? When is the bank out? When is the disk full? Resilience tests
  • • Unexpected types:In JavaScript/Python, what happens when you receive undefined, NaN, Infinity or an object where you expect string?
  • • Competition:Two simultaneous calls to the same function, timeout during operation, cancellation in the middle of a transaction
Code Example

💻Example in Terminal

# Request edge case testing specifically
> Read the processPayment function in src/payment.ts and ONLY generate edge case tests:
- Zero, negative, very large value (overflow)
- Invalid currency, null currency
- Payment gateway timeout
- Double processing (idempotency)
- Cancellation during processing
Practical Tip

💡Practical Tip

Ask Claude to think like a"adversary"from the code: "Try to break this function. What inputs would cause unexpected behavior, crash, or corrupted data?" This generates much more revealing tests than asking "write tests".

A powerful approach: ask Claude to list 20 possible edge cases, choose the 10 most relevant, and then ask him to generate tests just for those.
