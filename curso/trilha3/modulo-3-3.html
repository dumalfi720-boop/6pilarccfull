Workflow: Refactor Code

TOPIC 1
1

Understanding Current Architecture

Before refactoring a single line, you need todeeply understand the code that will change. Refactoring without understanding is a recipe for bugs. Claude Code reads the codebase and explains the current architecture before making any changes.

🎯Main Concept

The principle"read before change"is the foundation of all secure refactoring:

  • •Map dependencies:Which files import the module you want to refactor? Who depends on him? Interface changes affect all consumers
  • •Identify patterns:Does the code follow any specific standard? Are there naming, structure or organizational conventions that need to be maintained?
  • •Check existing tests:Are there tests that cover the current code? If not, create them before refactoring — they are your safety net

💡Practical Tip

Ask Claude to map out the architecture before any changes:

> Read module [X] and explain the current architecture. What are the dependencies? Who consumes this module? Are there existing tests?
TOPIC 2
2

Defining the Refactoring Objective

Refactoring without a clear objective becomesinfinite refactoring. Define exactly what you want to improve: performance? readability? testability? decoupling? Without a clear target, you could end up changing everything without improving anything.

🎯Main Concept

Um clear refactoring objectivehas three characteristics:

  • •Specific:"Extract the validation logic into a separate module" instead of "improve the code"
  • •Measurable:Can you check whether the objective was achieved? Fewer dependencies? Fewer lines? More tests passing?
  • •Behavior preserver:The external behavior must be identical. Refactoring changes the structure, not the functionality

💡Practical Tip

Communicate the objective explicitly:

> Refactor [module X] to [goal]. Don't change any external behavior. Keep the same public API.
TOPIC 3
3

Refactoring in Small Commits

The golden rule of refactoring:small, incremental commits. Each commit must be an atomic change that compiles, passes tests, and can be independently rolled back. Never do a giant refactoring in a single commit.

🎯Main Concept

Small incremental changesare the safest approach:

  • •One step at a time:Rename a variable, extract a function, move a file — each change is a separate commit
  • •Reversible:If something breaks, you can roll back the last commit without losing all progress
  • •Reviewable:Small commits are easier to review. A 20-line diff is easy to understand; one of 2000 lines no one reads

💡Practical Tip

Ask Claude to break down the refactoring into atomic steps:

> Break this refactoring into small, independent steps. Take one step at a time and commit after each one.
TOPIC 4
4

Keeping Tests Green

At each step of the refactoring,all tests must continue passing. If a test breaks, either the test is wrong (and needs to be updated) or the refactoring introduced a change in behavior (and needs to be fixed).

🎯Main Concept

Green tests after each changeis non-negotiable in refactoring:

  • •Rotate after each step:Don't accumulate changes without testing. Run the full suite after each atomic commit
  • •Tests that break = signal:A test breaking during refactoring indicates that you changed behavior. Investigate before updating the test
  • •Create tests first:If the code does not have adequate coverage, add tests before refactoring. They are your guarantee

💡Practical Tip

Automate verification after each step:

> After each change, run all tests and confirm that they pass before moving on to the next step.
TOPIC 5
5

Reviewing the Full Diff

After completing all the refactoring steps, do afinal review of full diff. Look at all the changes together and check that the end result is coherent, readable and genuinely improves the code.

🎯Main Concept

A final reviewchecks the holistic result:

  • •Macro view:Each individual commit makes sense, but does the whole thing improve the code? Is the end result cleaner?
  • •Consistency:Are the naming conventions consistent across the diff? Is there a mix of styles?
  • •Simplicity:Is the refactored code genuinely simpler or just different? Has unnecessary complexity been removed?

💡Practical Tip

Ask Claude to critically review the result:

> Review the full refactoring diff. Is the result genuinely better? Are there inconsistencies? Has anything become more complicated than before?
TOPIC 6
6

Safe Refactoring Patterns

They existrefactoring patterns that are inherently safeand others that are risky. Knowing the difference helps you choose the right changes and in the right order.

🎯Main Concept

Safe standards vs risky patterns:

  • •Insurance:Rename (variable, function, file), Extract Function, Extract Module, Move File, Inline Variable, Remove Dead Code
  • •Moderates:Change Signature, Extract Interface, Replace Conditional with Polymorphism
  • •Risky:Rewrite from scratch, Change data structures, Merge modules with different logic

💡Practical Tip

Always start with safe defaults and progress gradually:

> Start with renames and extractions (safe patterns). Only move on to structure changes after the basic standards are applied.
