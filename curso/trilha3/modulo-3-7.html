TOPIC 1

📋 Pasting errors directly

The fastest way to debug with Claude Code is simplypaste the stack trace or error messagedirectly into the conversation. Claude reads the error, identifies the file and line, analyzes the context and suggests the correction. Without needing to explain anything - the error speaks for itself.

Main Concept

🎯Main Concept

Claude is trained to interpret stack traces from practically any language: Python tracebacks, Node.js errors, Java exceptions, Go panics, Rust panics and much more. It automatically extracts thefile, line, function and type of errorto give an accurate diagnosis.

  • • Paste and ask:Literally copy the error from the terminal and paste it into Claude. It understands the format automatically
  • • Automatic context:Claude reads the file mentioned in the stack trace to understand the full context, not just the error line
  • • Diagnosis + fix:In addition to explaining the error, Claude suggests (and can apply) the correction immediately
  • • Build errors:Compilation errors, linting, TypeScript, webpack - all can be pasted and resolved
Example

💻Example in Terminal

# Simply paste the error
> TypeError: Cannot read properties of undefined (reading 'map')
at UserList (src/components/UserList.tsx:23:18)
at renderWithHooks (node_modules/react-dom/...)
# Claude will:
1. Read src/components/UserList.tsx
2. Identify that 'users' can be undefined on line 23
3. Suggest: users?.map() or loading state check
Practical Tip

💡Practical Tip

Don't filter the stack trace - paste itfull. Even the lines of internal frameworks (React, Express, Django) help Claude understand the execution context and provide a more accurate diagnosis.

If the error happened after a recent change, mention: "This error started appearing after I modified file X." This helps Claude focus on the probable cause.

TOPIC 2
2

📥 Log pipe (cat error.log | claude)

For large logs or error files, thepipe straight to Claudeand the most efficient approach. Instead of manually copying and pasting, you redirect the log file contents directly for analysis, leveraging the power of headless mode.

Main Concept

🎯Main Concept

The log pipe combines the power of Unix with the intelligence of Claude. You can filter, trim, and target specific logs for analysis without needing to open an interactive session. Claude receives the content via stdin and responds with the diagnosis.

  • • Direct pipe: cat error.log | claude -p "Analise estes erros"- sends the entire log for analysis
  • • Filtered with grep: grep ERROR app.log | claude -p "Classifique estes erros"- sends only the error lines
  • • Last N lines: tail -100 app.log | claude -p "O que aconteceu?"- analyzes the last 100 records
  • • Docker Logs: docker logs container_id 2>&1 | claude -p "Diagnostique"- container logs
Example

💻Example in Terminal

# Full log
$ cat /var/log/app/error.log | claude -p "Identify the 3 most critical errors and suggest fixes"
# Filtered by time
$ grep "2026-03-09" app.log | grep ERROR | claude -p "What caused these errors today?"
# Test output failing
$ npm test 2>&1 | claude -p "Analyze test failures and suggest corrections"
# Multiple service logs
$ docker-compose logs --tail=50 2>&1 | claude -p "Identify communication problems between services"
Practical Tip

💡Practical Tip

For very large logs (>1000 lines), filter before sending. Claude works best with focused context. Usetail -200, grep ERROR ou grep -A5 "Exception"to send only the relevant one.

Create an alias for quick debugging:alias debug-log='tail -200 | claude -p "Analise estes logs e identifique o problema"'

TOPIC 3
3

🔎 Tracing root cause (file analysis)

Finding the error is just the beginning - the real challenge is finding theroot cause. Claude Code excels at this because it can read multiple files, trace the chain of calls and identify where exactly the problem originates, even if the error appears elsewhere.

Main Concept

🎯Main Concept

Root cause analysis with Claude follows the principle of"5 Whys": the error appears on line X, but why? Because the variable is null. Why is it null? Because the fetch failed. Why did it fail? Because the URL is wrong in the config. Claude does this chain automatically, reading each relevant file.

  • • Call trace:Claude follows the stack trace, reading each file and function in the chain to find the real source of the problem
  • • Multi-file reading:Claude automatically reads the files referenced in the error, imports, configurations and dependencies
  • • Hypotheses and verification:Claude formulates hypotheses about the cause and checks each one by reading the relevant code
  • • Git history:When relevant, Claude can usegit log e git blameto identify when and who introduced the bug
Example

💻Example in Terminal

# Request root cause analysis
> This error appears in UserList.tsx:23 but I think the real cause is elsewhere. Trace the chain of calls and find the root cause:
TypeError: Cannot read properties of undefined (reading 'map')
# Claude will read:
1. UserList.tsx → identifies that 'users' comes from useQuery()
2. hooks/useUsers.ts → identifies that the fetch uses getApiUrl()
3. config/api.ts → finds incorrect URL in .env
Root cause: REACT_APP_API_URL not defined in .env.local
Practical Tip

💡Practical Tip

When the bug is mysterious, ask Claude to work on it.Plan Modefirst: "Before changing anything, analyze the problem and tell me where you think root is causing it." This avoids premature fixes that mask the real problem.

Usegit bisectwith Claude: "Run git bisect to find the commit that introduced this bug" - Claude can automate the entire process.

TOPIC 4
4

🔧 Applying the fix (correction + verification)

With the root cause identified, and time toapply the correction and checkthat works. Claude Code doesn't just suggest the fix - it edits the file, runs the tests and confirms that the error has been resolved. The complete debug cycle takes place in a single session.

Main Concept

🎯Main Concept

The fix cycle is:diagnosis → correction → test → verification. Claude performs all steps, ensuring that the fix not only resolves the original error but also does not introduce new problems (regressions).

  • • Surgical fix:Claude makes the smallest change possible to solve the problem, minimizing the risk of side effects
  • • Automatic check:After applying the fix, Claude runs the tests and/or reproduces the error scenario to confirm the resolution
  • • Regression test:Claude can generate a specific test for the bug, ensuring it doesn't return in the future
  • • Descriptive commit:Claude can create a commit with a message that describes the bug and fix for future reference
Example

💻Example in Terminal

# Request fix + full verification
> Fix the bug you identified. After:
1. Run the tests to confirm that the fix works
2. Create a regression test for this bug
3. Make a commit with a descriptive message
# Typical result:
Fix applied to src/config/api.ts
Regression test created in __tests__/api-config.test.ts
All 47 tests passing
Commit: "fix: add fallback for undefined API URL in config"
Practical Tip

💡Practical Tip

Always sin oneregression testalong with the fix. Testing ensures that the same bug never comes back. Without testing, you (or another dev) may reintroduce the same problem in the future.

Commit pattern for bugs:"fix: [o que foi corrigido] - [causa raiz]". Ex: "fix: prevent null crash in UserList - add API URL fallback"

TOPIC 5
5

🎲 Intermittent errors (flaky debugging)

The most frustrating errors areintermittent: Sometimes they happen, sometimes they don’t. Race conditions, timing issues, flaky tests and state-dependent errors. Claude Code can help identify patterns in these errors and suggest robust solutions.

Main Concept

🎯Main Concept

Intermittent errors generally have systematic causes that manifest themselves under specific conditions. Claude can analyzemultiple occurrences of the same error, identify patterns (time, load, status) and propose solutions that address the root cause.

  • • Race conditions:Two competing operations accessing the same resource. Claude identifies shared state and suggests locks, mutexes or restructuring
  • • Flaky tests:Tests that pass and fail randomly. Generally caused by dependence on timing, global state or execution order
  • • Pattern analysis:Collect several instances of the error and ask Claude to find what they have in common
  • • Reproduction:Claude can suggest how to reproduce the error consistently, which is half the solution
Example

💻Example in Terminal

# Analyze flaky test
> The "should update user profile" test fails intermittently (3 out of 10 runs). Analyze the test and the code it tests to find the cause of the blinking.
# Analyze multiple occurrence logs
$ grep "ConnectionTimeout" app.log | claude -p "Do these timeouts happen in patterns? What is the likely cause?"
Practical Tip

💡Practical Tip

For flaky tests, ask Claude to run the test 10 times in a loop and analyze the results:"Rode este teste 10 vezes. Se falhar em alguma, analise a diferenca entre as execucoes que passaram e as que falharam."

Intermittent errors in production: collect at least 5 occurrences before analyzing. A single occurrence may be noise, but 5 reveal patterns.

TOPIC 6
6

📊 Production logs (secure analysis)

Analyzing production logs requires extra care: they may containsensitive data(tokens, emails, IPs). Claude Code can help you diagnose production problems safely, as long as you follow good sanitization practices before sharing logs.

Main Concept

🎯Main Concept

Production logs are the richest source of information for debugging, but they come with responsibilities. Claude processes the logs locally on your machine, but it is good practicesanitize sensitive databefore sending for analysis.

  • • Sanitization:Remove tokens, passwords, emails and personal data before sending to Claude. Use sed/awk to mask
  • • Filtering by relevance:Do not send 10GB of logs. Filter by timestamp, severity level or specific service
  • • Event correlation:Claude can correlate logs from multiple services to trace the flow of a failed request
  • • Metrics and trends:In addition to specific errors, Claude can identify trends: "errors have increased by 300% in the last 2 hours"
Example

💻Example in Terminal

# Sanitize and analyze
$ cat prod.log | sed 's/Bearer [^ ]*/Bearer [REDACTED]/g' | \
sed 's/[a-zA-Z0-9._%+-]*@[a-zA-Z0-9.-]*/[EMAIL]/g' | \
claude -p "Analyze these production logs. Identify critical errors and patterns."
# Multiple service logs
$ kubectl logs -l app=api --tail=200 | claude -p "Correlate errors between pods"
Practical Tip

💡Practical Tip

Create a reusable sanitization script for your production logs. This makes it safe and quick to send logs for analysis without risk of data leakage.

Never send production logs with payment data, bank credentials, or API tokens. Usegrep -vto remove lines that contain sensitive keywords before the pipe.

PRACTICAL EXERCISE

🏋️Practical Exercise

Diagnose 3 different errors via log pipe and stack traces

1

Create error scenarios

Introduce 3 intentional bugs into the project and collect the errors:

# Bug 1: Undefined reference
# Bug 2: Incorrect import
# Bug 3: Wrong type of parameter
$ npm test 2>&1 > errors.log
2

Diagnose via pipe

Use pipe to send each error to Claude:

$ cat errors.log | claude -p "Identify all errors, trace the root cause of each one and suggest fixes"
3

Apply fixes and check

Ask Claude to correct each error interactively:

> Fix the 3 identified bugs. After each fix, run the tests to confirm.

All 3 errors should be resolved and tests passing.

4

Create regression tests

Ensure bugs don't return:

> Create a regression test for each of the 3 fixed bugs.
