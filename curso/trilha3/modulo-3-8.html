🗺️ Planning in Plan Mode

Multi-file migrations are the riskiest tasks in development. Before changing a single line of code, use thePlan Modefrom Claude to map the complete scope: which files will be affected, what dependencies exist and what is the safe order of execution.

🎯Main Concept

Plan Mode (activated withShift+Tabor setting the mode to "plan") makes Claudeanalyze without modifying. It reads the files, maps dependencies, and proposes a detailed execution plan before touching any code.

  • • Scope analysis:Claude lists all the files that need to change and why. No surprises in the middle of the migration
  • • Dependency map:Identifies which files depend on which, determining the safe order of modification
  • • Risk estimation:Claude evaluates which changes are mechanical (safe rename) versus which involve logic (higher risk)
  • • Defined batches:The plan divides the migration into batches of 3-5 files, each batch testable independently

💻Example in Terminal

# Activate Plan Mode and request analysis
> [Plan Mode] I need to rename the User model to Account throughout the project. Review the full scope:
- Which files will be affected?
- What dependencies exist between them?
- What is the safe order of execution?
- Divide into batches of a maximum of 5 files.
DO NOT modify anything yet.

💡Practical Tip

Never start a multi-file migration without a plan. The time invested in planning pays off 10x by avoiding inconsistent states where half the code uses the old name and half the new one.

Save Claude's plan in a file for reference:"Salve este plano de migracao em MIGRATION_PLAN.md"

📋 Identifying affected files

Claude Code can automatically map all files impacted by a change, usinggrep, import analysis and dependency tree. This ensures that no files are forgotten during the migration.

🎯Main Concept

Identifying impact goes beyond a simple “find and replace”. Claude analyzesimports, exports, types, interfaces, tests and documentationto assemble the complete list of affected files, including those that require indirect changes.

  • • Direct references:Files that directly import or use what is being modified
  • • Indirect references:Files that use via re-export, inheritance or composition
  • • Related tests:Test files that verify the behavior being modified
  • • Settings:package.json, tsconfig.json, .env, docker-compose.yml that may need tuning

💻Example in Terminal

> List ALL files that reference "UserService" directly or indirectly. Include imports, types, tests and configurations. Classify each file as: direct change, indirect change or test.

💡Practical Tip

Ask Claude to create a markdown checklist with all affected files. Mark each one as modified. This avoids the most common problem in migrations: forgetting a file.

Also check build configuration files (webpack, vite, tsconfig paths) that may have aliases or mappings to the old name.

TOPIC 3
3

⚡ Running in batches

Never modify all files at once. The execution inbatches of 3-5 filesallows you to detect problems early, keep the code compilable between batches and do partial rollback if necessary.

🎯Main Concept

Batch execution is the safest approach for large migrations. Each batch is a cohesive set of changes that can beindependently committed, tested and rolled back. If something breaks in batch 3, you only need to roll back batch 3, not the previous ones.

  • • Batch size:3-5 files and the sweet spot. More than that is difficult to review. Less and very slow
  • • Batch cohesion:Group files that depend on each other in the same batch to avoid broken intermediate states
  • • Batch commit:Make a commit after each successful batch. This creates safe restore points
  • • Instruction to Claude:"Run only batch 1 of the migration plan. DO NOT proceed to batch 2 without my confirmation."

💻Example in Terminal

# Run batch 1
> Run batch 1 of the plan: rename User to Account in models/user.ts, types/user.ts and interfaces/user.ts. Then stop and wait for my confirmation.
# After testing batch 1
> Batch 1 OK. Run batch 2: update the imports in services/auth.ts, services/profile.ts and controllers/user.ts.

💡Practical Tip

Start with the most "internal" files (models, types) and move on to the most "external" ones (controllers, routes, views). This ensures that dependencies are already updated when you reach consumers.

If the project uses TypeScript, keep the build running between batches: type errors immediately point out which references you forgot to update.

TOPIC 4
4

✅ Testing after each batch

Tests between batches are thesafety netof migration. After each batch, run tests, build and linting to confirm that the code is in a consistent state before proceeding. Without this, you accumulate problems that become impossible to diagnose.

🎯Main Concept

The batch cycle is:modify → test → commit → next batch. If the tests fail, you stop, fix it in the current batch and only then move forward. Never advance to the next batch with failed tests.

  • • Unit tests:Run after each batch to catch reference errors, broken imports and incorrect types
  • • Build/compile:For TypeScript, Go, Rust - run the build to catch type errors that tests may not cover
  • • Linting:ESLint, Pylint - catch unused imports, dead variables and other post-rename problems
  • • Checkpoint commit:Each tested and committed batch creates a safe point of return

💻Example in Terminal

> Batch 1 completed. Now:
1. Run npm run build to check for type errors
2. Run npm test to check tests
3. If everything passes, commit "refactor: rename User to Account - batch 1/4"
4. If it fails, fix it before continuing

💡Practical Tip

Use numbered commit messages for migrations:"refactor: rename User → Account (batch 1/4 - models)". This facilitates selective rollback and PR review.

If a batch fails and the fix is ​​not obvious, dogit stashand analyze the problem calmly before continuing.

TOPIC 5
5

🔍 Final sweep (complete scan)

After all batches, make onefinal sweep: a full scan to find forgotten references, hardcoded strings, outdated comments and any remnants of the old name/pattern that escaped the batches.

🎯Main Concept

The final sweep is the last line of defense. Claude makes aglobal grepby the old name/pattern throughout the project, including files that were not in the original plan - configurations, scripts, documentation, seeds and fixtures.

  • • Global grep:Search for the old name in ALL files, including .env, README, comments, strings, fixtures and seeds
  • • Full tests:Run the entire suite of tests, not just the unit tests. Integration and e2e can reveal problems that unitaries do not address
  • • Final review:Ask Claude to /review all the migration changes together
  • • Documentation:Update README, API docs and any documentation that references the old name/standard

💻Example in Terminal

> Perform a final sweep of the User → Account migration:
1. Grep for "User" (case-insensitive) throughout the project
2. Identify references that should have been renamed
3. Ignore false positives (e.g. "username" does not need to change)
4. Correct the missing ones
5. Run all tests again

💡Practical Tip

The final sweep often finds 5-10% of forgotten references, especially in log strings, error messages, database table names and test fixtures. Never skip this step.

Sweep in a separate commit:"refactor: rename User → Account - final sweep". This makes it clear in the git history what was planned vs what was caught in the sweep.

TOPIC 6
6

📦 /compact in long migrations

Multi-file migrations generate very long conversations with Claude. The context grows with each batch and Claude may lose focus. THE/compactand essential forkeep the context manageablewithout losing migration progress.

🎯Main Concept

In long migrations, the/compactsummarizes the conversation by keeping themigration plan, batches already completed and the current status. This reduces token consumption and improves the quality of responses in subsequent batches.

  • • When to compress:After every 2-3 full batches, or when you feel responses are becoming slow or inaccurate
  • • Targeted compact:Use/compact mantenha o plano de migracao e o status de cada batchto preserve the essential
  • • External plane:Keep the migration plan in a separate .md file so that Claude can re-read it after compacting
  • • Real savings:A migration of 20 files can consume 200k+ tokens without compact. With compact every 3 batches, it drops to 50-80k tokens

💻Example in Terminal

# After completing batch 3 of 6
> /compact keep: 1) complete migration plan, 2) batches 1-3 already completed and committed, 3) batches 4-6 pending with list of files
# Resume after compact
> Continuing the migration. Read MIGRATION_PLAN.md to remember the plan. Run batch 4.

💡Practical Tip

The ideal strategy is:plan in the file + compact in the conversation. The plan is persisted in MIGRATION_PLAN.md, and Claude can re-read it at any time. Conversation becomes lighter with regular compact.

For very large migrations (50+ files), consider using separate sessions for each group of batches, rather than a single session with compact.
