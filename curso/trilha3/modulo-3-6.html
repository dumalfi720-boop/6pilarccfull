📋 /review - Requesting automated review

The command/reviewand the entry point for AI-assisted code review. Claude analyzes all pending changes (staged and unstaged), reads the context of the modified files and generates astructured review reportwith problems categorized by severity.

Main Concept

🎯Main Concept

O /reviewIt works like having a senior reviewer available 24/7. It analyzes not only the diff, but also thefull context of modified files, understanding the impact of changes on the system as a whole.

  • • Complete analysis:Claude reads the diff, the complete affected files and related tests to give a contextualized review
  • • Problem categories:Bugs, security, performance, style, best practices - each issue is categorized for easy prioritization
  • • Actionable suggestions:Each comment comes with a concrete suggestion on how to resolve it, not just a vague criticism.
  • • Before PR:Use /review BEFORE creating the PR to catch issues early when they are cheaper to fix
Example

💻Example in Terminal

# Simple review of current changes
> /review
# Review focused on one aspect
> Review my changes focusing on security and error handling
# Review of a specific file
> Review changes to src/auth/login.ts with a focus on vulnerabilities
Practical Tip

💡Practical Tip

knife/reviewa habit before each commit. Even if you're working alone, automated review catches mistakes that your tired eyes don't see. And how to have pair programming without needing another dev.

Tip: rotate/reviewafter each significant block of work, not just at the end. Smaller, more frequent reviews are more effective.

TOPIC 2
2

⚠️ Severity levels

Claude organizes the review findings intofour severity levels: Critical, Important, Minor and Nitpick. This classification helps you prioritize what to fix now versus what can wait, making the review actionable rather than overwhelming.

Main Concept

🎯Main Concept

Not every problem has the same urgency. Severity classification allows you tofocus on what mattersand don't waste time on cosmetic details when there are critical bugs to resolve.

  • • Critical:Bugs that cause crashes, data loss, security vulnerabilities. They must be corrected BEFORE the merge. Ex: SQL injection, null pointer in production
  • • Important:Logic problems, poor performance, missing error handling. They must be corrected in this PR. Ex: N+1 query, lack of input validation
  • • Minor:Code improvements, readability, conventions. Good fix, but it doesn't block the merge. Ex: poorly named variable, duplicate code
  • • Nitpick:Stylistic preferences, formatting, comments. Totally optional. Ex: import order, white space
Example

💻Review Output Example

🔴 CRITICAL: SQL Injection in getUserById()
Line 45: Query built with string concatenation.
Fix: Use prepared statements with parameters.
🟠 IMPORTANT: Fetch() lacks error handling
Line 78: No catch for network failure.
🟡 MINOR: Function too long (87 lines)
Consider extracting into smaller functions.
⚪ NITPICK: Variable 'x' could have a better name
Practical Tip

💡Practical Tip

Rule of thumb:always fix Critical and Important before merging. Minor can go as a follow-up. Nitpick is optional. If Claude marks something as Critical, stop everything and resolve it immediately.

You can instruct Claude about the level of rigor: "Review with maximum rigor, treating any security issues as Critical" or "Review lightly, focusing only on bugs".

TOPIC 3
3

🔧 Correcting review feedback

After receiving the review, the next step isresolve the identified problems. Claude doesn't just point out problems - he can fix them directly. You can ask him to resolve all Criticals, or go item by item, validating each correction.

Main Concept

🎯Main Concept

The correction flow is iterative:review → correct → review again. Claude maintains the context of the previous review and is able to verify that each problem was effectively resolved without introducing new problems.

  • • Automatic fix:Ask Claude to fix all Critical and Important issues at once: "Fix all issues marked as Critical and Important in the review"
  • • Selective fix:Address one issue at a time to maintain control: "Fix the SQL injection on line 45 using prepared statements"
  • • Re-review:After the corrections, run /review again to confirm that everything has been resolved and no new problems have been introduced
  • • Discussion:If you disagree with a finding, explain why. Claude may recognize that it was a false positive or provide more context
Example

💻Example in Terminal

# Fix all Critical
> Fix all issues marked as Critical in the previous review.
# Check if it has been resolved
> /review
# Disagree with a finding
> The item about long and intentional function - it needs to be atomic for transaction reasons. You can ignore it.
Practical Tip

💡Practical Tip

Carry out a maximum of 2 rounds of review/correction. If after 2 iterations there are still problems, the approach probably needs to be rethought rather than more patches.

Run the tests after each round of fixes to ensure the fixes didn't break anything:"Corrija os problemas do review e rode os testes para confirmar que nada quebrou."

TOPIC 4
4

🚀 /pr - Automatically creating pull request

The command/prcreates a complete pull request on GitHub/GitLab withautomatically generated title, description, labels and summary. Claude analyzes all commits in the branch, understands the context of the changes and generates a professional description of the PR.

Main Concept

🎯Main Concept

O /prautomates the most tedious part of the PR workflow: writing the description. Claude reads all commits, diffs and CLAUDE.md of the project to generate aDescriptive PR, with context and review checklist.

  • • Clever title:Claude generates a concise title that describes what the PR does, not how it does it
  • • Full description:Includes motivation, changes made, impact, testing, and instructions for the reviewer
  • • Automatic checklist:Generates a review checklist based on changes (tests added? docs updated? breaking changes?)
  • • Integration with gh CLI:Claude uses the GitHub CLI (gh) internally to create the PR directly in the repository
Example

💻Example in Terminal

# Create PR automatically
> /pr
# PR with specific instructions
> Create a PR for the current branch. Include in the description: motivation, changes and how to test. Add label "feature".
# Typical result:
PR #42 created: "Add user authentication with JWT"
https://github.com/org/repo/pull/42
Practical Tip

💡Practical Tip

Always ride/reviewbefore the/pr. The ideal flow is: code → /review → fix → /review (confirm) → /pr. This ensures that the PR comes out clean.

Add a PR template to CLAUDE.md so that Claude follows your team's standard: title with prefix (feat:, fix:, chore:), mandatory sections and standard labels.

TOPIC 5
5

🎯 Focused review (security, performance)

In addition to the general review, you can ask Claude to dospecialized reviewsfocused on a specific aspect: security, performance, accessibility, compliance or any other criteria. This is like having different experts review the same code.

Main Concept

🎯Main Concept

Focused reviews are deeper than general reviews because Claude focuses all of his attention ona single aspect. Instead of covering everything superficially, it dives deep into security, performance, or whatever focus you define.

  • • Security review:Injection, XSS, CSRF, authentication, authorization, sensitive data exposure, vulnerable dependencies
  • • Performance review:N+1 queries, unnecessary rendering, memory leaks, inefficient algorithms, missing caching
  • • Accessibility review:ARIA labels, color contrast, keyboard navigation, screen reader compatibility
  • • Combination:Run focused reviews in sequence to get complete coverage: first security, then performance, then general
Example

💻Example in Terminal

# Security review
> Do a security review of my changes. Focus on: injection, XSS, authentication, data exposure and vulnerable dependencies.
# Performance review
> Review with a focus on performance. Identify N+1 queries, unnecessary renders, large objects in memory and caching opportunities.
Practical Tip

💡Practical Tip

For critical changes (payment, authentication, personal data), always carry out a dedicated security review in addition to the general review. The general review may pick up on security issues, but a focused review goes much deeper.

Create a checklist on CLAUDE.md: "For PRs that touch on auth/, payments/ or user-data/, always run a focused security review."

TOPIC 6
6

🔄 Complete PR flow (end-to-end)

Now that you know each piece, let's assemble thecomplete end-to-end workflow: from finishing the code to having the PR approved and ready for merge. This flow combines review, correction, testing and PR creation in a fluid and efficient process.

Main Concept

🎯Main Concept

The complete flow follows 6 steps:Code → Review → Fix → Test → Re-review → PR. Each step feeds into the next, and Claude maintains context throughout the entire process.

  • • 1. Finalize the code:Make sure all changes are saved and the correct files are staged
  • • 2. /general + focused review:Run general review and, if applicable, security review. Note the Critical and Important findings
  • • 3. Correct the findings:Ask Claude to fix the identified problems, starting with the Critical ones
  • • 4. Run tests:Confirm that the fixes didn't break anything and that the new scenarios are covered
  • • 5. Re-review:Run /review again to confirm everything is clean. If there are still problems, repeat 3-4
  • • 6. /pr:Once everything is clear, create the PR with automatic description and send it for human review
Example

💻Full Flow

> /review
# Claude finds 2 Critical, 3 Important
> Correct all Critical and Important.
# Claude applies the corrections
> Run the tests to confirm that nothing broke.
# Everyone passes
> /review
# Clean - only 1 Nitpick
> /pr
# PR #42 created with full description
Practical Tip

💡Practical Tip

Add this flow as an instruction in the project's CLAUDE.md:"Antes de criar qualquer PR, sempre rode /review, corrija Critical/Important, rode testes, e so entao use /pr."

This flow takes 5-10 minutes with Claude Code versus 30-60 minutes manually. And the quality gain is consistent - Claude never forgets to check security or run tests.
