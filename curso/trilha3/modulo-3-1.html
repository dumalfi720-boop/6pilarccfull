1

Identifying the Bug

Every bug fix starts with aclear description of the symptom. The more accurate you are in describing the problem to Claude Code, the faster he will find the root cause. Don't just say "it's broken" — describe what happens, when it happens, and what should happen.

Main Concept

🎯Main Concept

The quality of the diagnosis directly depends on the quality of the symptom description. Claude Code needs three essential pieces of information to launch an effective investigation:

  • • Symptom:What is going wrong? What is the observed behavior? An error message, an incorrect result, a crash, a timeout?
  • • Reproduction:What steps reproduce the bug? Does it happen all the time or intermittently? In which environment (dev, staging, production)?
  • • Expectation:What should happen instead of the bug? What is the correct expected behavior?
Practical Tip

💡Practical Tip

Use this template to describe bugs to Claude Code. It works as astructured bug reportwhich maximizes the chance of correct diagnosis on the first attempt:

$ claude "There is a bug where [symptom]. Happens when [reproduction steps]. Expected [correct behavior]."
═══════════════════════════ ════════════════════════════ TOPIC 2: Forcing investigation before fix ═══════════════════════════ ════════════════════════════
2

Forcing Investigation Before Fix

One of the most common mistakes is asking Claude Code to"fix the bug" without first investigating. This leads to superficial fixes that treat the symptom but not the root cause. The secret is to force reading and diagnosis before making any changes to the code.

Main Concept

🎯Main Concept

The approach"read first, diagnose second, fix third"is the key to lasting corrections. When you ask Claude to read the relevant files before suggesting any changes, he builds a more complete mental model of the problem.

  • • Read first:Ask Claude to read the relevant files and trace the logic of the flow where the bug occurs
  • • Diagnose:Ask for an explanation of the root cause before seeing any fix suggestions
  • • Confirm:Validate that the diagnosis makes sense with your knowledge of the system before authorizing changes
Practical Tip

💡Practical Tip

Use this prompt to force investigation before fixing:

> Read the relevant files and trace the logic before suggesting any fixes. I want to understand the root cause first.

Claude will use the Read, Grep and Glob tools to investigate the codebase, and only then present a structured diagnosis. This avoids the default"kick and pray"which generates secondary bugs.

═══════════════════════════ ════════════════════════════ TOPIC 3: Pasting complete stack traces ═══════════════════════════ ════════════════════════════
3

Pasting Complete Stack Traces

Stack traces arepure gold for diagnosis. Each line of the stack trace tells a part of the story: where the error happened, which function called which, and at what point the execution failed. Don't summarize, don't cut — paste the complete stack trace.

Main Concept

🎯Main Concept

The full context of the error and what allows Claude Codenavigate directly to relevant files and lines. A complete stack trace contains file names, line numbers and the chain of calls that led to the error.

  • • Paste everything:Complete stack traces, error messages, warnings. Don't summarize — Claude needs the details to find the exact file and line
  • • Inclua contexto:What command did you run? Which endpoint was called? Which input generated the error? The context surrounding the error is as important as the error itself
  • • Use pipe:For errors in log files, usecat error.log | claude -p "O que esta causando estes erros?"to feed Claude directly
Practical Tip

💡Practical Tip

When pasting an error into Claude Code, include as much context as possible. Claude will automatically use the tools to navigate to the files mentioned in the stack trace:

> I'm getting this error when running npm test:
[paste the complete stack trace here]
Please help me identify and fix the root cause.
═══════════════════════════ ════════════════════════════ TOPIC 4: Applying the fix safely ═══════════════════════════ ════════════════════════════
4

Applying the Fix Safely

After confirming the diagnosis, it is time to apply the fix. Buta fix without testing and a time bomb. The correct workflow is: apply the fix, run existing tests and, ideally, add a test that covers the bug scenario to ensure it never returns.

Main Concept

🎯Main Concept

The pattern"fix + test"and non-negotiable. Every bug fix must be accompanied by automated verification:

  • • Apply the fix:Let Claude make the necessary changes. Review the diff carefully before accepting — pay special attention to side effects
  • • Run the tests:Ask Claude to run the full test suite. If any test breaks, the fix may be incorrect or incomplete
  • • Add regression test:Ask Claude to create a test that reproduces the original bug and verifies that the fix resolves it. This is your guarantee against future regressions
Practical Tip

💡Practical Tip

Use this prompt to ensure the fix includes verification:

> Fix the bug and run tests to make sure nothing else broke. Add a regression test for this scenario.
═══════════════════════════ ════════════════════════════ TOPIC 5: Committing the fix ═══════════════════════════ ════════════════════════════
5

Committing the Correction

With the fix applied and the tests passing, it's time torecord the correction in the project history. The command/commitfrom Claude Code analyzes your changes and generates a descriptive commit message automatically.

Main Concept

🎯Main Concept

O /commitIt's not a simplegit commit. It analyzes the diff, understands the context of the changes, and generates a semantic commit message that explains the "why" of the change, not just the "what":

  • • Automatic analysis:Claude reads the diff and understands which files changed, which functions were changed and what the purpose of the change was
  • • Semantic message:Generates messages in the conventional format (fix:, feat:, refactor:) with a clear description of what was fixed
  • • Review before confirming:You see the generated message and can accept, edit or reject it before the commit is made
Practical Tip

💡Practical Tip

After confirming that the tests pass, simply type:

> /commit

Claude will analyze all staged and unstaged changes, generate a commit message and ask if you want to commit. It's the fastest and most consistent way to maintain a clean commit history.

═══════════════════════════ ════════════════════════════ TOPIC 6: Post-mortem: learning from the bug ═══════════════════════════ ════════════════════════════
6

Post-mortem: Learning from the Bug

The bug is fixed, but the work doesn't end there. The final — and most underrated — step isunderstand why the bug existed in the first place. This turns each bug fix into a learning opportunity that prevents similar future bugs.

Main Concept

🎯Main Concept

A root cause analysisanswers questions that go beyond the immediate fix:

  • • Why did the bug exist?Was it a logic error, a lack of validation, an edge case not considered, or a change in another part of the system that caused a side effect?
  • • Why wasn't he caught earlier?Were there any tests missing? Didn't the code review cover it? Was the documentation incomplete?
  • • How to prevent?What rules, tests or standards can we add so that bugs of this type never slip through again?
Practical Tip

💡Practical Tip

After committing the fix, ask Claude for a post-mortem analysis:

> Please explain the root cause of this bug. Why did it exist? Why wasn't he caught earlier? What can we do to prevent similar bugs?

Claude's answers may reveal gaps in your CLAUDE.md, missing tests or code patterns that need strengthening. Use these insights toupdate project documentation.
