Workflow: Build New Feature

TOPIC 1
1

Starting in Plan Mode

The biggest mistake when building new andstart coding before planning. Claude Code's Plan Mode is a special mode where Claude analyses, designs and proposes a complete architecture without writing a single line of code. This saves tokens, avoids rework and produces more cohesive features.

🎯Main Concept

O Plan Modeand activated with Shift+Tab or asking Claude to "enter plan mode". In this mode, it analyzes the codebase, identifies where changes need to happen, and creates a detailed plan before touching any files:

  • • Design first:Claude maps which files need to be created or modified, what dependencies exist and what is the best architectural approach
  • • Token Economy:Planning ahead costs a fraction of what rewriting code after a wrong approach
  • • Full view:You see the entire plan before approving, and can adjust the approach before any implementation

💡Practical Tip

Start any new feature with this prompt:

> I want to add [feature description]. Go into plan mode and design the approach before writing any code.

Claude will read the codebase, understand the existing architecture and propose a plan. Only approve when you are satisfied with the approach.

TOPIC 2
2

Reviewing the Plan

The plan generated by Claude is not to be accepted blindly.Review architecture, tradeoffs, and decisionsbefore approving the implementation. This is the cheapest time to change direction.

🎯Main Concept

When reviewing the plan, evaluate three critical dimensions:

  • • Architecture:Is the feature being added in the right place? Does it follow existing project standards? Does it create unnecessary coupling?
  • • Tradeoffs:What are the alternatives? Did Claude choose the simplest approach? Is there unnecessary complexity?
  • • Scope:Does the plan cover all requirements? Are there edge cases not considered? Will the feature work in all scenarios?

💡Practical Tip

Ask about alternatives and tradeoffs before approving:

> What alternatives did you consider? What are the tradeoffs of the chosen approach? Is there a simpler approach?
TOPIC 3
3

Step-by-Step implementation

With the plan approved, implementation begins. Butdon't get it all at once. Build incrementally, checking each step before moving on to the next. This reduces the risk of cascading errors and makes debugging easier if something goes wrong.

🎯Main Concept

A incremental constructionfollows the principle of “make it work first, then improve”:

  • • Core first:Implement the basic functionality that makes the feature work in the simplest scenario
  • • Add layers:Validations, error handling, edge cases and optimizations are added in subsequent steps
  • • Check each step:After each increment, check that everything still works before moving on.

💡Practical Tip

Break large features into smaller tasks and tackle them one at a time:

> Start by implementing [part 1 of the plan]. Just this part for now.
...review, test...
> Now implement [part 2]. Keep what we've already done working.
TOPIC 4
4

Testing During Construction

Tests are not something for "later".Write tests along with the implementation, ideally before (TDD) or immediately after each component. This ensures that you detect problems early, when the cost of fixing them is low.

🎯Main Concept

The pattern"test alongside"This means that each feature increment is accompanied by tests:

  • • Unit tests:For each new function or method, create tests that cover the happy path and edge cases
  • • Integration tests:For interactions between components, verify that the complete flow works
  • • Rotate frequently:After each breaking change, run the test suite to catch regressions early

💡Practical Tip

Request tests along with each part of the implementation:

> Now write tests for what we just implemented. Cover the happy path and edge cases. Run the tests.
TOPIC 5
5

Polish and Final Review

Before committing, do afinal quality review. This includes code cleanup, checking edge cases, documentation and ensuring that the feature follows project standards.

🎯Main Concept

O final polishtransforms functional code into production code:

  • • Cleanup:Remove console.logs, ALL temps, commented code and unused imports
  • • Edge cases:Think about invalid inputs, error states, competition, performance limits
  • • Consistency:Check that the feature follows the naming, structure and style standards of the rest of the project

💡Practical Tip

Ask Claude for a critical review of what was built:

> Review everything we just built. Is there something we missed? Edge cases? Cleanup necessary? Does the code follow project standards?
TOPIC 6
6

From Commit to PR

The feature is ready. Now is the time topack everything for delivery: clean commit with semantic message and pull request with clear description. The commands/commit e /prautomate this process.

🎯Main Concept

The flow/commit + /prand the natural closure of any feature:

  • • /commit:Analyzes the diff, generates semantic message (feat:, fix:, refactor:) and creates the commit with your approval
  • • /pr:Analyzes the commits in the branch, generates the title and description of the PR and creates the PR on GitHub automatically
  • • Revision:You can edit both the commit message and the PR description before committing

💡Practical Tip

The complete delivery flow in two commands:

> /commit
...review and approve the message...
> /pr
...review and approve the PR...
