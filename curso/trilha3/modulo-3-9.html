👥 What are Agent Teams (multi-agent)

Agent Teams and Claude Code's experimental functionality that allowsmultiple Claude agents working simultaneouslyin different subtasks of the same project. Instead of a single sequential agent, you have a team of specialized agents operating in parallel.

🎯Main Concept

Agent Teams transforms Claude Code from asolo agent into a team coordinator. The main agent (orchestrator) receives the task, divides it into subtasks and delegates to subagents working in parallel, each in its own isolated git worktree.

  • • Orchestrator:The main agent receives its task, plans the division and coordinates the subagents. It doesn't edit code directly
  • • Subagents:Independent agents that receive specific subtasks and work in parallel, each with their own session
  • • Isolation:Each subagent works in a separate git worktree, avoiding concurrent editing conflicts
  • • Final merge:After all subagents complete, the orchestrator merges the changes and resolves conflicts

💻Usage Example

# Task that benefits from Agent Teams
> Implement full authentication in this project:
- Backend: JWT + refresh tokens + middleware
- Frontend: Login page + AuthContext + protected routes
- Tests: Unit + integration tests for both
# The orchestrator can delegate:
Subagent 1: Backend auth (models, routes, middleware)
Subagent 2: Frontend auth (components, context, pages)
Subagent 3: Tests (unit + integration)

💡Practical Tip

Agent Teams works best when subtasks areindependent of each other. If subagent A needs the result of subagent B to start, parallelism doesn't help. Think of tasks that can be performed at the same time without dependencies.

Ideal examples: implementing frontend and backend simultaneously, writing tests while another agent writes code, migrating different modules in parallel.

⚙️ Enabling Agent Teams

Agent Teams is an experimental feature that needs to beexplicitly enabledvia environment variable. As it is experimental, it may change between versions, but it is already stable enough to be used in real projects.

🎯Main Concept

Activation is done by configuring the environment variableCLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1. This enables the built-in tooldispatch_agentthat the orchestrator uses to create and manage subagents.

  • • Environment variable: export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1in your shell or .bashrc
  • • Verification:After activating, turn/statusand confirm that "Agent Teams" appears as enabled
  • • Requirements:Git installed (for worktrees), disk space (each worktree is a copy), and enough API limit for parallel calls
  • • Cost:Agent Teams consumes more tokens because multiple agents work simultaneously. Monitor with /cost

💻How to Enable

# Activate for current session
$ export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
$ claude
# Activate permanently
$ echo 'export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1' >> ~/.bashrc
$ source ~/.bashrc
# To check
> /status
Agent Teams: enabled (experimental)

💡Practical Tip

Activate Agent Teams only when you are going to use it. In simple tasks, the overhead of coordination and worktrees is not worth it. Use for large, parallelizable tasks. For everyday life, normal mode is more efficient.

Make sure your repository is in a clean state (no uncommitted changes) before starting Agent Teams. Worktrees work best from a clean git state.

📤 Subagents and task delegation

With Agent Teams enabled, Claude can use the tooldispatch_agenttocreate subagents with specific tasks. Each subagent receives clear instructions, works independently and reports the result to the orchestrator.

🎯Main Concept

The delegation follows the standard oftask decomposition: the orchestrator divides the large task into smaller subtasks, creates a subagent for each one with specific instructions, and waits for the results to combine everything.

  • • Clear instructions:Each sub-agent receives a specific prompt with a well-defined scope: what to do, where to do it and what not to touch
  • • Shared context:The project's CLAUDE.md is accessible to all subagents, maintaining consistency of style and conventions
  • • Parallel execution:The subagents work at the same time, each in their own worktree. Orchestrator monitors progress
  • • Result report:Each subagent reports: what was done, which files were modified and whether the tests pass

💻Example of Delegation

# The orchestrator decides to delegate like this:
dispatch_agent("API Subagent") →
"Implement REST endpoints for product CRUD
in src/routes/products.ts. Use the default of other routes."
dispatch_agent("Subagent Tests") →
“Write tests for product endpoints.
Cover full CRUD, validation and errors."
dispatch_agent("Docs Agent") →
"Update the API documentation with the new endpoints
of products in OpenAPI format."

💡Practical Tip

The quality of the delegation depends on the clarity of the instructions. Be specific: instead of "implement the backend", say "implement the GET /products, POST /products, PUT /products/:id and DELETE /products/:id endpoints in src/routes/products.ts following the pattern in src/routes/users.ts".

Avoid circular dependencies between subagents. If the testing sub-agent needs code from the API sub-agent, they cannot run in parallel. In this case, use sequential execution.

🔄 Autonomous agentic loop

The agentic loop is when the Claude Code operates inautonomous for extended periods, making decisions, executing actions and self-correcting without human intervention. With Agent Teams, this loop multiplies - each sub-agent has its own autonomous loop.

🎯Main Concept

The agentic loop follows the cycle:Observe → Think → Act → Verify → Repeat. Claude observes the current state, thinks about the next action, executes it, checks the result and decides whether he needs to continue. This loop runs until the task is complete or a limit is reached.

  • • Please note:Read files, run tests, check git status to understand the current situation
  • • Think:Plan the next action based on what you observed and the objective of the task
  • • Act:Edit files, run commands, create tests - execute the planned action
  • • Verify:Run tests, build and linting to confirm that the action had the expected effect

💻Loop in Action

# Task that triggers an agentic loop
> Add input validation to all API endpoints. For each endpoint:
1. Identify accepted parameters
2. Add validation with zod
3. Create test for validation
4. Run the tests and correct if necessary
Repeat for all endpoints.
# Claude goes into a loop:
→ Le routes/users.ts (Note)
→ Plan schema zod for POST /users (Think)
→ Add validation + test (Act)
→ Run npm test (Verify)
→ Go to GET /users/:id (Repeat)

💡Practical Tip

The agentic loop is most effective when you defineclear completion criteria: "For when all endpoints have validated AND all tests pass." Without clear criteria, the loop may become undefined or stop too soon.

Use/costafter long loops. A loop of 20+ iterations can consume a lot of tokens. Set limits: "If the cost exceeds $2, stop and let me know."

🌳 Isolated worktrees (git worktree)

The technical basis of Agent Teams are thegit worktrees: each sub-agent works on an isolated copy of the repository, avoiding conflicts when multiple agents edit files at the same time. Understanding worktrees is fundamental to using Agent Teams effectively.

🎯Main Concept

A git worktree and aadditional work directorylinked to the same git repository. Each worktree can be in a different branch and have independent modifications. Claude creates temporary worktrees for each subagent and removes them after the merge.

  • • Complete insulation:Each subagent edits files in its own worktree without affecting the others. No editing conflicts
  • • Separate branches:Each worktree operates in its own branch, facilitating later merging
  • • Even .git:All worktrees share the same git repository, saving space and keeping the history unified
  • • Automatic Cleanup:After the merge, Claude removes the temporary worktrees automatically

💻How It Works

# What Claude does internally:
# 1. Create worktree for subagent
$ git worktree add ../agent-1-api feature/agent-1-api
# 2. Subagent works on worktree
$ cd ../agent-1-api && claude -p "Implement..."
# 3. Merge back
$ git merge feature/agent-1-api
# 4. Cleanup
$ git worktree remove ../agent-1-api

💡Practical Tip

Worktrees consume disk space (each is basically a copy of your project, minus the .git). In large projects (>1GB), monitor available space before creating multiple worktrees.

You can also use worktrees manually (without Agent Teams) to work on multiple tasks simultaneously:git worktree add ../feature-x feature/x.

6

🧭 When to use and when to avoid

Agent Teams and agentic loop are powerful tools, butnot for every task. Knowing when to use it is just as important as knowing how to use it. The coordination overhead, cost of tokens and risk of conflicts make this decision critical.

🎯Main Concept

The decision framework is simple:If the task can be done by a single agent in less than 30 minutes, don't use Agent Teams. The coordination overhead only pays off when there is real parallelism and the task is large enough.

  • • Use when:Task has 3+ independent subtasks, would take >1h for a solo agent, involves different areas of the codebase (frontend + backend + tests)
  • • Avoid when:Task is sequential (each step depends on the previous one), involves few files (<5), or requires design decisions that need human supervision
  • • Cost:Agent Teams consume 2-4x more tokens than a solo agent. Justified when the time speedup compensates the extra cost
  • • Risk:More agents = more chances of conflict in the merge. Minimize by assigning non-overlapping file areas to each subagent
Do vs Avoid

✓ Good candidates for Agent Teams

  • ✓ Implement full-stack feature (API + UI + tests)
  • ✓ Migration of 20+ files with independent areas
  • ✓ Generate tests for multiple modules simultaneously
  • ✓ Refactoring + documentation + parallel testing

✗ Avoid Agent Teams for

  • ✗ Bug fix in a single file
  • ✗ Tasks with high dependency between subtasks
  • ✗ Architectural decisions that need oversight
  • ✗ Very small projects (<10 files)

💡Practical Tip

Get started with Agent Teams in taskslow risk(test generation, documentation) before using it to implement critical features. This allows you to understand the behavior and limits of the tool without risking production code.

Rule of thumb: if you don't trust the result of a single agent for the task, don't trust the result of multiple agents. Agent Teams amplifies capacity, but it also amplifies errors.

🏋️Practical Exercise

Configure Agent Teams and perform multi-agent tasking

1

Enable Agent Teams

Configure the environment variable and check:

$ export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
$ claude
> /status

Confirm that Agent Teams appears as enabled.

2

Define parallelizable task

Choose a task that has independent subtasks:

> Generate unit tests for the modules: auth, products and orders.
Each module can be tested independently.
Use subagents to work in parallel.
3

Monitor execution

Watch the subagents work and monitor the cost:

> /cost

Write down the total time and cost. Compare that to how much it would take with a solo agent.

4

Check result and merge

Confirm that everything was merged correctly and the tests pass:

$ npm test
$ git log --oneline -10

All tests must pass and subagents' commits must be in history.
