🧩 What are Self-Validating Prompts

A self-validating prompt and a prompt that includesyour own verification criteria. Instead of you manually reviewing whether Claude did everything right, the prompt instructs Claude to check the work before declaring it complete. And how to deliver a task with a built-in acceptance checklist.

Main Concept

🎯Main Concept

The difference between a normal prompt and a self-validating one:

// NORMAL PROMPT:
"Add input validation to the signup form."

// SELF-VALIDATING PROMPT:
"Add input validation to the signup form.

Before completing marking, verify:
□ Email format validated (regex + DNS check)
□ Password meets requirements (8+ chars, 1 upper,
1 number, 1 special)
□ Error messages are user-friendly (not technical)
□ XSS prevented on all inputs
□ Tests cover valid + 3 invalid scenarios
□ All existing tests still pass

Report status of each box."
  • • Explicit checklist:Claude knows exactly what needs to be ready. There is no space for "I forgot to add tests"
  • • "Report status":Asking Claude to report the status of each item forces him to check each one before responding
  • • Reduces review cycles:Instead of you discovering that XSS prevention was missing in the review, the prompt already requires this before concluding
  • • Document expectations:The checklist functions as documentation of what "done" means for that specific task
Practical Tip

💡Practical Tip

Createreusable checklistsfor common task types. One checklist for "new feature", another for "bug fix", another for "API endpoint". Save to CLAUDE.md or as snippets. Over time, your self-validating prompts become instant to write.

The phrase "Before marking complete, verify" is the trigger. Without it, Claude may or may not check. With her, he ALWAYS checks.

📏 Adding Verification Criteria

Effective verification criteria arespecific, measurable and automatically verifiable. "Code must be good" is not a criterion. "All tests pass and there are no lint errors" is a criterion. In this topic, you learn how to write criteria that actually work.

Main Concept

🎯Main Concept

The 4 types of verification criteria and how to write them correctly:

// 1. AUTOMATIC (Claude can check by running command)
□ `npm test` passes with 0 failures
□ `npm run lint` reports 0 errors
□ `npm run build` completes without errors

// 2. INSPECTION (Claude checks by reading the code)
□ No hardcoded secrets or API keys
□ All new functions have JSDoc comments
□ Error messages are in Portuguese

// 3. BEHAVIORAL (Claude checks logically)
□ Empty list returns empty array, not null
□ Invalid email shows specific error message
□ Concurrent requests don't cause race conditions

// 4. NEGATIVES (which should NOT exist)
□ No console.log statements in production code
□ No TODO comments left behind
□ No new npm dependencies added
  • • Automatics are the strongest:Claude can literally turn the controller and see what happens. No ambiguity, no interpretation
  • • Inspection works well:Claude reads the code and checks it. Works for visible patterns such as naming, comments and formatting
  • • Negatives prevent regressions:Saying what should NOT exist is as important as what should. "No console.log" avoids debug trash in production
Practical Tip

💡Practical Tip

Start with criteriaautomatics(tests and lint) and add 2-3 inspection criteria or negatives relevant to the task. Don't overdo it: 5-8 criteria per task is ideal. More than 10 dilutes the focus.

For CI/CD projects, align the prompt criteria with the pipeline checks. If the CI runs lint + tests + build, its criteria should mirror this.

📋 Prompts with Built-in Checklists

Built-in checklists go beyond verification criteria. They guide Claudeduring execution, not just at the final check. Each step in the checklist is a step that Claude must complete and check off, creating a visible trail of progress.

Main Concept

🎯Main Concept

A prompt with a built-in checklist has three sections: task, execution checklist, and verification checklist:

[Task description]

Execution checklist (do in order):
□ Step 1: [specific action]
□ Step 2: [specific action]
□ Step 3: [specific action]
□ Step 4: Run tests

Verification checklist (check after completion):
□ All tests pass
□ No lint errors
□ [domain-specific check]

Report: mark each item ✅ or ❌ with notes.
  • • Two separate checklists:Execution (during) and verification (after). This ensures that Claude follows the process AND validates the result
  • • Order matters:"Do in order" guarantees sequential execution. Useful when step 2 depends on step 1
  • • Visual report:Requesting an appointment with check/x creates a visual report that you can scan in seconds
Practical Tip

💡Practical Tip

Use built-in checklists torepetitive tasks you do frequently. New module setup, deployment checklist, code review checklist. Save as a template in CLAUDE.md and reuse with small adaptations.

The marked report allows you to quickly identify what failed. If Claude marks something as x, you know exactly where to intervene, without reading the entire output.

🔁 Automatic Verification Loop

The automatic check loop is the most advanced level of self-validating prompts. Instead of checking once at the end, you instruct Claude toContinuously check and automatically correctuntil all criteria pass. It's like a CI pipeline that runs until it's green.

Main Concept

🎯Main Concept

The check loop prompt has a repeat until all criteria are met:

[Task description]

After implementation, run this verification loop:

1. Run `npm test` - if failures, fix and re-run
2. Run `npm run lint` - if errors, fix and re-run
3. Run `npm run build` - if errors, fix and re-run
4. Check: no hardcoded values, no console.logs
5. Check: all new code has error handling

Repeat until ALL checks pass.
Maximum 3 iterations. If still failing after 3,
report what's blocking and ask for guidance.
  • • Automatic loop:Claude executes, checks, corrects, checks again. You receive the final result already validated
  • • Iteration limit:"Maximum 3 iterations" prevents infinite loops. If after 3 attempts it still fails, it probably needs human intervention
  • • Human fallback:"Report what's blocking and ask for guidance" ensures that Claude doesn't get stuck. It scales for you when needed
  • • Order matters:Tests first, lint second, build last. If the tests fail, there is no point checking the lint
Practical Tip

💡Practical Tip

The check loop works best withautomatic criteria(tests, lint, build). For inspection criteria, use checklists instead of loops, as Claude has no way to "re-run" a visual inspection in a different way.

In projects with CI/CD, you can go further: "After all local checks pass, push to a feature branch and verify CI passes. If CI fails, fix locally and push again."

📊 Confidence Scoring (Asking Claude to Rate)

Confidence scoring is a technique where you ask Claude toassess your own confidence in the result. This reveals areas of uncertainty that you can review more closely. A Claude who says "90% confident" is more reliable than one who says "100% confident" about a complex task.

Main Concept

🎯Main Concept

The confidence scoring prompt asks for self-assessment by dimension:

[After completing the task]

Rate your confidence (0-100%) on each dimension:

- Correctness: __% (does it do what was asked?)
- Completeness: __% (all edge cases covered?)
- Security: __% (no vulnerabilities?)
- Performance: __% (no bottlenecks?)
- Test coverage: __% (all paths tested?)

For any dimension below 85%, explain what's
uncertain and what would increase your confidence.
  • • Forced metacognition:Asking Claude to evaluate himself activates "thinking about thinking". He reconsiders the work under each dimension
  • • 85% Threshold:Any dimension below 85% requires explanation. This reveals where Claude has doubts and where you should focus your review
  • • "What would increase confidence":This question is gold. Claude might say "integration tests would increase my confidence in correctness" — and you can ask him to write them
  • • Calibration with experience:Over time, you learn how Claude calibrates his notes. 95% is generally solid. 70% deserve immediate attention
Practical Tip

💡Practical Tip

Combine confidence scoring with the verification loop:"For any dimension below 85%, take action to increase it before declaring done."This transforms diagnostic scoring into automatic corrective action.

Be 100% suspicious in any dimension. If Claude says 100% security for a complex feature, it may be a lack of critical thinking, not real confidence. In this case, run a separate Security Audit.

🔄 Complete Validated Prompt System

Now let's combine everything into onecomplete system of self-validating prompts. This is the final workflow of Track 4: a universal template that you can adapt to any task, ensuring that Claude's output always meets the quality standards you have defined.

Main Concept

🎯Main Concept

The universal self-validating prompt template combines outcome delegation, checklists and confidence scoring:

##Outcome
[What I want to achieve - declarative]

##Constraints
[What must NOT change, tech restrictions]

## Execution Steps
[Ordered checklist of what to do]

## Verification
[Automated checks + inspection checks]
Run verification loop (max 3 iterations).

## Confidence Report
Rate correctness, completeness, security (0-100%).
For any below 85%, take corrective action.
  • • 5 clear sections:Outcome (what), Constraints (limits), Execution (how), Verification (checking), Confidence (self-assessment). Each section has a specific role
  • • Adaptable:For simple tasks, use Outcome + Verification. For complex tasks, use the full template. The framework is modular
  • • Document in CLAUDE.md:Add the template as the project default. Claude will automatically follow this structure in future tasks

This template encapsulates the entire Track 4:Daily Drivers (module 4.1), Getting Started (4.2), Building (4.3), Testing (4.4), Quality (4.5), Architecture (4.6), Outcome Delegation (4.7) and now Verification (4.8). You have the complete system.

Practical Tip

💡Practical Tip

Don't treat the template as rigid.Adapt to each context. An urgent hotfix needs quick Outcome + Verification. A critical feature needs the complete template with 10+ verification criteria. The goal is to have a structure, not a prison.

With the completion of this module, you have mastered the entire Track 4. The next time you open Claude Code, you'll have an arsenal of professional prompts that generate senior-level results, automatically verified and validated.
