TOPIC 1: Structured Bug Report
1

📝 Structured Bug Report (Full Template)

You already know the Structured Bug Report from module 4.1. Now let's delve deeper intoComplete template with all variations: visual bugs, data bugs, integration bugs and performance bugs. Each type has nuances that change the diagnosis.

🎯Main Concept

The base template with extensions for specific bug types:

Bug type: [visual | date | integration | performance]
When I do [action], I get [error].
Expected: [...]
Current: [...]
Environment: [browser/OS/version]
Reproducibility: [always | sometimes | rare]
Stack trace: [paste]

Investigate root cause before attempting a fix.
  • •Bug type:Classifying the type helps Claude focus on the right area. Visual bugs require CSS/layout inspection. Data bugs require analysis of queries and transformations
  • •Environment:Bugs that only happen in Safari, or only on mobile, or only on Windows. This information completely changes the diagnosis
  • •Reproducibility:"Always" is easy to debug. "Sometimes" suggests race condition or state management. "Rare" could be memory leak or edge case

💡Practical Tip

For visual bugs,describe the expected vs current layout in words. "The button should be aligned to the right of the container, but it appears in the center" is much more useful than "the layout is wrong". If possible, include screen dimensions and breakpoints.

TOPIC 2: Log Analysis
2

📊 Log Analysis Prompt

Application logs can be hundreds of lines long. The Log Analysis prompt makes Claudeautomatically parse, group and prioritize errors. Instead of you reading line by line, it identifies patterns, groups related errors and pinpoints the root cause of the most critical ones.

🎯Main Concept

Here are logs:
[paste]

1. Identify distinct errors
2. Group related ones
3. Rank by severity
4. Trace root cause of critical ones
  • •Smart Grouping:50 "connection refused" errors are not 50 problems - they are 1 problem that manifested itself 50 times. Claude identifies this
  • •Ranking by severity:Critical (system down), High (broken functionality), Medium (degradation), Low (cosmetic warning). You know what to attack first
  • •Root cause of critics:Claude doesn't just identify the error - he traces it back to the cause. "Connection refused in PostgreSQL indicates that the connection pool has been exhausted, probably due to N+1 queries on the /users endpoint"

💡Practical Tip

For very large logs,use Claude Code to read log files directlyinstead of copying and pasting. Say: "Read the file /var/log/app.log and analyze errors from the last hour." Claude uses the Read and Grep tools to process the file on the server.

TOPIC 3: Stack Trace Diagnosis
3

🔍Stack Trace Diagnosis

Stack traces are the best clue to finding bugs, but many developers don't know how to read them completely. The Claude Codele stack traces with surgical precision: identifies the exact line of the problem, navigates to the file, and understands the surrounding context.

🎯Main Concept

I'm getting this error:
[paste full stack trace]

1. Identify the exact line causing the error
2. Read that file and surrounding context
3. Explain why this error occurs
4. Suggest fix with explanation
  • •Automatic navigation:Claude reads the stack trace, finds the files mentioned in your project, and opens them to understand the context. No need for anything manual
  • •Surrounding context:It's not enough to see the error line. Claude analyzes the functions that call, the data that arrives, and the conditions that led to the error
  • •Fix with explanation:Claude doesn't just fix it - he explains why the error happened and why the fix works. This builds understanding for next time

💡Practical Tip

Always paste thefull stack trace, not just the last line. The intermediate lines show the chain of calls and often reveal the real problem, which may be far above the line where the error actually occurred.

TOPIC 4: Intermittent Bug
4

👻 Intermittent Bug Prompt

Bugs that happen "sometimes" are the hardest to resolve. Race conditions, state leaks, cache stale, timing issues. The Intermittent Bug prompt guides Claude toinvestigate the most common causes of non-deterministic bugs.

🎯Main Concept

I have an intermittent bug: [describe]
It happens approximately [frequency].

Investigate these common causes:
1. Race conditions (async/concurrent operations)
2. Stale cache or state
3. Timing-dependent logic
4. Resource exhaustion (connections, memory)
5. External dependency flakiness
  • •Race conditions:Two async operations that depend on each other but have no synchronization. Claude looks for unawaited promises, lockless shared state, and transactionless banking operations
  • •State/cache stale:Cached data that is out of date, React state that does not update when it should, localStorage with old data
  • •Resource exhaustion:Connection pool that exhausts under load, memory leaks that only appear after hours of use, file descriptors that are not closed

💡Practical Tip

For intermittent bugs,add temporary logs before trying fixes. Ask Claude: "Add debug logging to [area] so we can capture the state when this bug occurs next." After reproducing with logs, you have concrete data for diagnosis.

TOPIC 5: Performance Debugging
5

⚡ Performance Debugging

"It's slow" is not a bug report. Performance debugging requiresspecific metrics and systematic investigation. The Performance Debugging prompt guides Claude to find N+1 queries, I/O bottlenecks, unnecessary renders, and network bottlenecks.

🎯Main Concept

[endpoint/page/function] is slow. Takes [X]ms, should be under [Y]ms.

Investigate:
1. Database queries (N+1, missing indexes, full table scans)
2. Unnecessary computations or re-renders
3. Network waterfalls (sequential API calls)
4. Memory allocation patterns
5. Missing caching opportunities
  • •N+1 queries:The most common performance problem. Claude analyzes the code and identifies loops that perform individual queries instead of batch/join
  • •Network waterfalls:Sequential API calls that could be parallel. Turning 5 sequential requests into Promise.all() can cut time by 80%
  • •Concrete metrics:Always say how long it takes and how much it should take. "500ms but it should be 50ms" gives Claude a clear target

💡Practical Tip

After Claude identifies the bottleneck, ask himmeasure before and after: "Fix this performance issue and add a console.time/timeEnd to verify the improvement." This way you have concrete proof that the fix worked.

TOPIC 6: Production Incident Workflow
6

🚨 Production Incident Workflow

When something breaks down in production, you are under pressure. The Production Incident workflow is aOptimized prompt sequence for quick diagnosis under stress. Screening, diagnosis, fix, validation and post-mortem - all structured.

🎯Main Concept

The production incident workflow follows 5 steps:

  • •1. Rapid screening:"Production is down. Error: [error]. Read recent changes (git log -5) and identify the most likely cause. Be fast." - Focus on speed, not perfection
  • •2. Focused diagnosis:Use Log Analysis or Stack Trace Diagnosis on the specific error. Don't try to understand everything, just the immediate cause
  • •3. Minimum Fix:"Fix this with the smallest possible change. No refactoring. Just stop the bleeding." - In production, minimum fix and king
  • •4. Validation:"Verify this fix resolves the issue without introducing new problems." - Claude checks side effects
  • •5. Post-mortem:After the crisis, use Teach Me to understand what happened and how to prevent it in the future

💡Practical Tip

In production incidents,resist the temptation to refactor. Claude can suggest an elegant fix that changes 10 files. In production, you want to change 1 line that stops the bleeding. Refactoring comes later, calmly, with testing.
