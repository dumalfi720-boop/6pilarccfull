🧠 What is Outcome Delegation (vs Imperative)

Outcome Delegation is a fundamental change in the way you write prompts. Instead of giving step-by-step instructions (imperative), youdescribes the desired end result and success criteria(declarative). Claude chooses the path. It's like the difference between telling a taxi "turn right, then left" versus "take me to the airport."

Main Concept

🎯Main Concept

The fundamental difference between the two styles:

// IMPERATIVE (as most do):
"Create a file called auth.ts. Add a function called
login that takes email and password. Use bcrypt to
hash. Return a JWT token."

// OUTCOME DELEGATION (2026 technique):
"I need user authentication in this project.
Outcome: users can register, login, and access
protected routes. Sessions persist across browser
restarts. Failed logins are rate-limited.
Success criteria: all auth tests pass, in OWASP
vulnerabilities, follows project conventions."
  • • Why it works better:Claude in 2026 knows millions of implementations. When you describe the result, it chooses the best approach for YOUR specific project
  • • Imperative limits:By saying "use bcrypt", you prevent Claude from suggesting argon2 if it is more suitable. By saying "create auth.ts", you prevent a better file structure
  • • Outcome releases:You define WHAT and the restrictions. Claude decides HOW, using his knowledge of the project, conventions and best practices
  • • It's not "do anything":Outcome Delegation and precise results. What changes is that you don't micromanage the way
Practical Tip

💡Practical Tip

Start practicing with tasks that you already know how to solve. Write the imperative prompt as you normally would, thenrewrite as outcome delegation. Compare the results. In most cases, outcome delegation generates better code because Claude has the freedom to apply patterns that you may not know.

Rule of thumb: if you're telling Claude WHAT function to create and WHAT library to use, you're being too imperative. Describe the behavior, not the implementation.

2

🔄 From Imperative to Declarative (Rewriting)

The transition from imperative to declarative does not happen overnight. There is arewriting technique in 3 stepswhich makes conversation easier. You take any imperative prompt and systematically transform it into an outcome delegation.

Main Concept

🎯Main Concept

The 3 steps to convert any imperative prompt into an outcome delegation:

// Step 1: Identify the RESULT
Imperative: "Add a debounce to the search input"
Result: "Search doesn't fire on every keystroke"

// Step 2: Define SUCCESS criteria
"Search fires only after user stops typing for 300ms.
No duplicate requests. Loading state visible."

// Step 3: Add RESTRICTIONS (not implementation)
"Must work with existing search component.
No new dependencies unless justified."
  • • Step 1 - Result:Ask “what changes for the end user?” Instead of "add debounce", the result is "search does not fire on each key"
  • • Step 2 - Criteria:How do you know it worked? Measurable and observable definitions. "300ms delay" is a criterion. "It works well" is not
  • • Step 3 - Restrictions:Don't say HOW to solve it (use lodash debounce). Say what CANNOT happen (no new dependencies). Claude finds the best path within the restrictions
Practical Tip

💡Practical Tip

When you get an imperative prompt to rewrite, do the"taxi test": Imagine that you are delegating to a senior developer who knows the project. Would you say "create an auth.ts file with login function using bcrypt"? Or would you say "I need secure authentication, users must be able to log in and access protected routes"?

The second and outcome delegation. You trust Claude's competence and focus on the result, not the step-by-step process.

3

📋 Defining Expected Results

The quality of the outcome delegation directly depends on theclarity with which you describe the result. A vague result generates vague code. An accurate result generates accurate code. In this topic, you learn how to structure results that leave no room for misinterpretation.

Main Concept

🎯Main Concept

Use the OSCAR framework to define clear results:

O - Outcome (what changes in the system)
S - Scope (which parts of the system are affected)
C - Constraints (what should NOT change)
A - Acceptance (how to check that it is correct)
R - Risks (what could go wrong)
  • • Precise outcome:"Users can reset their password via email" and of course. "Improve password functionality" is vague. The more specific the outcome, the better the result
  • • Scope defined:"Affects auth module and email service. Does not touch user profile or settings." This prevents Claude from modifying areas you don't want
  • • Explicit constraints:"Existing login flow must not change. Token expiration stays at 24h." Constraints prevent unwanted side effects
  • • Verifiable Acceptance:"Test: request reset, receive email within 30s, click link, set new password, login with new password succeeds." Claude can self-check
Practical Tip

💡Practical Tip

You do not need to use the full OSCAR framework for every task. For simple tasks,Outcome + Acceptancethat's enough. Reserve the full framework for complex features that touch multiple modules.

Tip: add OSCAR as a template in your CLAUDE.md. Claude will learn to ask for this information when you give vague prompts, creating a positive feedback loop.

4

✅ Built-in Success Criteria

Built-in success criteria are the secret weapon of outcome delegation. Instead of manually checking if Claude did it right, youInclude the criteria in the prompt itselfand Claude checks himself. This dramatically reduces the cycle of “do it, review it, ask for correction, review it again”.

Main Concept

🎯Main Concept

Success criteria can be functional, technical and negative (which should NOT happen):

Outcome: [describe what you want]

Success criteria:
Functional:
- User can [action] and sees [result]
- Edge case [X] is handled gracefully

Technical:
- All existing tests still pass
- New test cover happy path + 2 edge cases
- No new linting errors

MUST NOT:
- Break existing [feature]
- Add dependencies without justification
- Expose [sensitive data] in logs

Check all criteria before marking complete.
  • • Functional criteria:What the end user observes. They are the most important and the easiest to check
  • • Technical criteria:Testing, linting, performance. Claude can check automatically by running the commands
  • • Negative criteria:"Must NOT" is as important as "must". Prevents regressions and side effects
Practical Tip

💡Practical Tip

The magic phrase and"Verify all criteria before marking complete". This makes Claude run tests, check linting and check each criterion before saying he's finished. Without this phrase, it may skip the check.

Start with 3-5 criteria per task. Many criteria overload the context. Few criteria leave room for error. The sweet spot is enough to cover the essentials without being excessive.

5

🔀 Practical Conversation Examples (Before/After)

Nothing teaches better than real examples. Here are practical conversions from imperative prompts to outcome delegation, coveringcommon everyday scenarioswith Claude Code.

Main Concept

🎯Main Concept

5 real-world conversions from imperative to outcome delegation:

// 1. CRUD Feature
BEFORE: "Create a users CRUD with Express routes,
Prisma models, and Jest tests"
AFTER: "I need full user management. Users can be
created, listed, updated, deleted. All operations
validated. All endpoints tested. Follow project patterns."

// 2. Bug Fix
BEFORE: "Add a null check on line 42 of UserService"
AFTER: "UserService crashes when user has no profile.
Outcome: service handles missing profiles gracefully.
No user-facing errors. Logged for debugging."

// 3. Performance
BEFORE: "Add Redis caching to the products endpoint"
AFTER: "Products endpoint takes 2s. Needs to be under
200ms. Cache invalidation on product updates. Stale
acceptable date for 60s."
  • • CRUD:Note that the "after" does not mention Express, Prisma or Jest. Claude uses what is already in the project. If the project uses Fastify and Drizzle, it uses Fastify and Drizzle
  • • Bug Fix:Instead of "add null check" (which may not be the best solution), the outcome describes the desired behavior. Claude can solve it with null check, default value, or restructuring
  • • Performance:Instead of "use Redis" (may not be the best option), the outcome defines the performance target. Claude can use Redis, in-memory cache, CDN, or optimize the query
Practical Tip

💡Practical Tip

Practice "mental rewriting" whenever you write a prompt. Before submitting, ask:"Am I describing the outcome or the path?"If you're telling Claude what function to create, what library to use, or what file to edit, you're being imperative.

Exception: if you have a specific reason for a technology ("use Redis because we already have it in production"), include it as a constraint, not as an instruction. "Constraint: we already run Redis in production, prefer it for caching."

6

⚖️ When to Use and When Not to Use

Outcome Delegation is not the answer to everything. There are situations where the imperative style is more efficient and situations where the declarative style shines. To knowWhen to use each styleThis is what separates an advanced user from an intermediate user.

Main Concept

🎯Main Concept

Decision guide for choosing the right style:

  • • USE Outcome Delegation when:The task is complex (multiple files), you are not sure of the best implementation, you want Claude to use project conventions, or you want senior level results
  • • USE Imperative when:You know EXACTLY what you want (variable rename, specific fix), the task is trivial (less than 5 lines), or you need a specific implementation for technical reasons
  • • USE Hybrid when:You want outcome delegation but with specific restrictions. "Outcome: X. Constraint: must use Y approach because Z." This combines freedom with direction
  • • AVOID Outcome for:Very specific infrastructure tasks (CI/CD configuration), changes that require exact format (SQL migrations), or when you have a mandatory team standard

General rule:If the task takes more than 10 minutes to describe imperatively, use outcome delegation. If it takes less than 1 minute, use imperative. In the middle? Use hybrid.

Practical Tip

💡Practical Tip

In practice, most of your prompts will behybrid. You define the outcome (declarative) but include important constraints (directives). "I need a notification system. Users get notified of new messages in real-time. Constraint: use WebSocket because we already have the infrastructure. Must NOT use polling."

The objective is not to eliminate the imperative. And have another tool in your arsenal. Over time, you will naturally feel which style is best suited to each situation.
