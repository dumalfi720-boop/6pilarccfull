⚖️ Architecture Decision Prompt (Compare Options)

Architectural decisions are the most expensive to reverse. Choosing between monolith and microservices, between SQL and NoSQL, between SSR and SPA, can define the success or failure of the project. The Architecture Decision prompt forces Claude tocompare options systematicallybefore recommending.

Main Concept

🎯Main Concept

The Architecture Decision prompt follows the ADR (Architecture Decision Record) format adapted for interaction with AI:

I need to decide: [decision to make].

Context:
- Team size: [N developers]
- Expected scale: [users/requests]
- Timeline: [deadline]
- Constraints: [budget, tech stack, team skills]

Compare options with:
1. Pros and cons of each
2. Complexity to implement
3. Long-term maintenance cost
4. Risk assessment
5. Your recommendation and why
  • • Context and crucial:The best architecture for 3 devs is different from the best for 30. Claude needs to know the real context to recommend correctly
  • • Structured comparison:Instead of asking "what should I use?", you ask for a comparative analysis. This eliminates confirmation bias
  • • Maintenance cost:The quickest option to implement is not always the best. Claude evaluates the total cost over time
  • • Justified recommendation:Claude not only compares, but recommends. And explains the reasoning, so you can agree or disagree based on facts
Practical Tip

💡Practical Tip

Save the Architecture Decision output asADR in the repository(docs/adr/ folder). Documented architectural decisions are invaluable when someone asks "why did we do it that way?" in 6 months.

After the recommendation, follow-up: "Now assume I chose [option]. What are the first 5 things I should implement to set up this architecture correctly?"

2

🔌 Design Prompt API (REST API)

Poorly designed APIs create pain for years. Inconsistent naming, missing pagination, non-existent versioning, non-standard error responses. API Design prompt makes Claude designProfessional APIs from the first endpoint, following good REST and industry practices.

Main Concept

🎯Main Concept

The API Design prompt covers all dimensions of a well-designed API:

Design a REST API for [domain/feature].

Include:
1. All endpoints (method + path + description)
2. Request/response schemas (with examples)
3. Authentication strategy
4. Pagination approach
5. Error response format (consistent)
6. Versioning strategy
7. Rate limiting recommendations

Follow REST best practices and use consistent naming.
  • • Full endpoints:Claude generates the entire list of endpoints with correct HTTP method, semantic path and clear description
  • • Schemas with examples:Request and response bodies with real examples. This serves as instant documentation
  • • Consistent format error:A standard format for errors (e.g. {error: {code, message, details}}) throughout the API. Facilitates frontend and integrators
Practical Tip

💡Practical Tip

After generating the API design, ask Claude:"Now generate the OpenAPI 3.0 spec for this API."You receive a YAML file that can be imported directly into Swagger UI, Postman or any API documentation tool.

For public APIs, add: "This API will be consumed by third-party developers. Include comprehensive documentation, clear error messages, and idempotency keys for write operations."

3

🗄️ Database Schema Prompt

The database schema is the foundation of everything. A poorly designed schema generates complex queries, poor performance and painful migrations. The Database Schema prompt does Claudemodel data thinking about queries, performance and evolutionof schema over time.

Main Concept

🎯Main Concept

The Database Schema prompt goes beyond "create tables". It considers the actual use of data:

Design a database schema for [domain].

Requirements:
- [list main entities and relationships]
- [list main queries/access patterns]

Include:
1. Tables with columns, types, and constraints
2. Indexes optimized for the query patterns above
3. Foreign keys and relationships
4. Normalization decisions (and when to denormalize)
5. SQL Migration
  • • Access patterns first:Define how the data will be read before defining how it will be stored. This guides indexing and denormalization decisions
  • • Optimized indexes:Claude creates indexes based on the query patterns you listed. Not generic indexes, but indexes that speed up your real queries
  • • Standardization decisions:Not everything should be normalized. Claude explains when to denormalize for performance and when to keep normalized for consistency
  • • SQL migration ready:The output already includes the migration SQL that you can run directly or adapt to your project's ORM
Practical Tip

💡Practical Tip

Always list themost frequent access patternsat the prompt. "Users will query orders by date range with status filter" is much more useful than "I need an orders table". Claude optimizes composite indexes for exactly these patterns.

After the initial schema, ask: "Now stress-test this schema. What happens with 10M rows in orders? What queries will become slow? What indexes should we add proactively?"

🌐 System Design Prompt (Distributed)

System design goes beyond a single service. It involves multiple components, communication between services, queues, caches, CDNs and fault tolerance. The System Design prompt makes Claudethink like a distributed systems architect, considering scalability, resilience and costs.

Main Concept

🎯Main Concept

The System Design prompt covers all layers of a distributed system:

Design a system for [use case].

Scale requirements:
- [N] daily active users
- [N] requests per second (peak)
- [N] GB data stored

Include:
1. High-level architecture diagram (text)
2. Service boundaries and responsibilities
3. Data flow for main use cases
4. Caching strategy
5. Queue/async processing needs
6. Failure scenarios and mitigation
7. Estimated infrastructure costs
  • • Real numbers:Providing DAU, RPS, and data volume allows Claude to scale correctly. Without numbers, the design becomes too generic
  • • Failure scenarios:What happens if the cache drops? If a service becomes unavailable? Claude designs fallbacks and circuit breakers
  • • Estimated costs:Claude estimates infrastructure costs based on the numbers provided. This helps validate that the design fits within the budget
Practical Tip

💡Practical Tip

Use the System Design prompt not only for new projects, but also forunderstand and document existing systems. Describe the current components and ask: "Given this current architecture, identify bottlenecks and propose an evolution path for 10x the current scale."

For early-stage startups: "Design this for 1000 users initially, but plan the architecture so it can scale to 1M users without a complete rewrite. Show what changes at each scale milestone."

5

🔄 Migration Planning Prompt

Migrations are the riskiest tasks in software engineering. Migrate database, change framework, update major version, move to cloud. Each one can break everything if poorly planned. The Migration Planning prompt forces Claude toplan migrations with zero-downtime and guaranteed rollback.

Main Concept

🎯Main Concept

The Migration Planning prompt creates a detailed plan with phases, rollback and verification:

Plan a migration from [current] to [target].

Current state: [describe current setup]
Target state: [describe desired end state]
Constraint: zero downtime required

Provide:
1. Step-by-step migration phases
2. Rollback plan for each phase
3. Data migration strategy
4. Verification checks between phases
5. Risk assessment per phase
6. Estimated timeline
  • • Incremental phases:Never migrate everything at once. Claude divides it into phases that can be executed and verified independently
  • • Rollback per phase:Each phase has its own rollback plan. If phase 3 fails, you only go back to phase 3, not the entire project
  • • Check between phases:Automatic checks that confirm that each phase has been completed successfully before moving on to the next
Practical Tip

💡Practical Tip

The secret to successful migrations is thepattern "strangler fig": the new system grows in parallel with the old one until it completely replaces it. Mention this in the prompt: "Use strangler fig pattern. Both systems run in parallel during migration."

Always ask for a timeline estimate per phase. "Phase 1: 2 days, Phase 2: 1 week" helps you plan sprints and communicate with stakeholders about migration progress.

🔍 Architecture Review Workflow

The Architecture Review combines all of the previous prompts into onecomplete workflow to evaluate and improve existing architecture. Instead of designing from scratch, you feed Claude with the current architecture and he identifies problems, suggests improvements and prioritizes changes.

Main Concept

🎯Main Concept

The Architecture Review workflow follows 4 steps to evaluate any existing system:

  • • Step 1 - Mapping:"Read the codebase and describe the current architecture. Include: services, databases, APIs, queues, external integrations." Claude maps what exists
  • • Step 2 - Analyze:"Given this architecture, identify: single points of failure, scaling bottlenecks, coupling issues, and technical debt." Claude points out problems
  • • Step 3 - Proposal:"Propose improvements prioritized by: impact (high/medium/low) and effort (days/weeks/months)." Claude suggests prioritizing
  • • Step 4 - Roadmap:"Create a migration roadmap from current to target architecture. Group changes into quarters." Claude generates the evolution plan

Important:Each step uses the output of the previous one. Don't skip steps. The precise mapping in step 1 is the basis for correct analyzes in the following steps.

Practical Tip

💡Practical Tip

Run Architecture Reviewquarterlyin active projects. Architecture evolves organically and problems gradually accumulate. A quarterly review catches tech debt before it becomes critical.

Share the output with the team. The mapping of step 1 is especially valuable for onboarding new members. They gain a complete view of the system in minutes.

Practical Exercise

  4. 4. Ask Claude to generate theOpenAPI 3.0 specificationof your API
