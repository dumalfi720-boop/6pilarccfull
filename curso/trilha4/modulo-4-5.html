🔬 Brutal Audit in Detail (Full Audit Prompt)

In module 4.1 you met Brutal Audit as Daily Driver. Now let's dissect the complete prompt, understand each audit dimension, and learn how tocustomize the audit for different contexts. Full audit is the most powerful prompt to ensure code quality before a merge or deploy.

Main Concept

🎯Main Concept

Full Audit Prompt expands the original 5 dimensions to a complete audit with structured output. You ask Claude to categorize each finding by severity and provide suggested fixes:

I just built [feature/module]. Perform a brutal audit.

For each finding, provide:
- Severity: CRITICAL / HIGH / MEDIUM / LOW
- Category: security | performance | edge case | crash | maintainability
- File and line number
- Description of the issue
- Suggested fix

Be brutally honest. I want zero surprises in production.
  • • Structured output:Categorization by severity allows prioritization. Solve CRITICALs immediately, HIGHs before the merge, MEDIUMs in the next sprint
  • • File and line number:Claude points out exactly where the problem is. You can get straight to the point without searching
  • • Suggested fix:Each finding already comes with a correction suggestion. You can ask "fix all CRITICALs" and Claude applies the corrections
  • • Focused Scope:Audit one module at a time. Auditing the entire project generates output that is too long and loses focus
Practical Tip

💡Practical Tip

Get into the habit of running Full Auditbefore each Pull Request. Include the audit output as a comment in the PR. This demonstrates diligence and saves the reviewer time. Many teams in 2026 already adopt this as part of the standard workflow.

Power tip: Add project context to the audit. "This is a financial application handling real money" completely changes the level of rigor that Claude applies to security auditing.

🛡️ Security Audit (OWASP, Vulnerabilities)

Security Audit is a specialized prompt that focuses exclusively on security vulnerabilities. It references theOWASP Top 10and checks against the most common and dangerous vulnerabilities. Ideal for applications that deal with sensitive data, payments or authentication.

Main Concept

🎯Main Concept

The Security Audit prompt is specific and targeted. You list the vulnerability categories you want to check:

Perform a security audit on [module/feature].

Check against OWASP Top 10:
- Injection (SQL, NoSQL, OS command)
- Broken authentication/session management
- Sensitive data exposure
- XSS (stored, reflected, DOM)
- Insecure deserialization
- CSRF vulnerabilities
- Missing rate limiting

For each finding, rate as CRITICAL/HIGH/MEDIUM/LOW
and provide the exact fix.
  • • OWASP as a framework:Using the OWASP Top 10 as a reference gives Claude a clear and comprehensive checklist to follow
  • • Injection and #1:Claude checks all database queries, system calls and any point where user input arrives without sanitization
  • • Rate limiting:Often forgotten, but critical. Endpoints without rate limiting invite brute force and DDoS attacks
Practical Tip

💡Practical Tip

Run Security Audit separately from the general Brutal Audit. The security audit deservesfull focus. When you mix security with performance and edge cases, security findings tend to become diluted.

For financial or healthcare apps, add: "This handles PII/financial data. Apply maximum security scrutiny. Assume attacker has access to client-side code."

3

⚡ Performance Audit (N+1, Memory, Bundle)

Performance problems are silent. Everything works perfectly with 10 users and collapses with 10,000. The Performance Audit prompt forces Claude tothink on scaleand identify bottlenecks before they become production fires.

Main Concept

🎯Main Concept

Performance Audit covers the most common categories of bottlenecks in modern applications:

Perform a performance audit on [module/feature].

Check for:
1. N+1 query problems
2. Missing database indexes
3. Memory leaks (event listeners, closures, caches)
4. Unnecessary re-renders (React/Vue)
5. Bundle size issues (large imports)
6. Missing caching opportunities
7. Blocking operations on main thread

Estimate impact: how many ms/MB each fix would save.
  • • N+1 queries:The most common problem in ORMs. Claude identifies loops that perform one query per iteration and suggests eager loading or batch queries
  • • Memory leaks:Event listeners not removed, closures that reference large objects, unlimited caches. Claude tracks the life cycle of objects
  • • Bundle size:Import the entire library when you only need one function. Claude suggests tree-shaking and selective imports
  • • Impact estimate:Asking for "estimate impact" forces Claude to quantify the gain. This helps you prioritize which optimizations are worth the effort
Practical Tip

💡Practical Tip

Run Performance Auditafter features that involve lists, tables or dashboards. These are the areas where N+1 queries and unnecessary re-renders cause the most damage. A table with 100 rows making 100 extra queries can transform a 200ms page into 5 seconds.

Combine with real data: "This endpoint currently takes 800ms. Find what's causing the bottleneck and suggest optimizations to get it under 200ms."

📝 Code Review Prompt (PR-Level Review)

The Code Review prompt simulates asenior reviewer examining your Pull Request. It looks not just for bugs, but for readability, conventions, naming, separation of concerns and everything a good reviewer would check. Use before opening the PR or while waiting for human review.

Main Concept

🎯Main Concept

The Code Review prompt is different from Brutal Audit. While the audit focuses on bugs and security, the review focuses onquality, readability and maintenance:

Review these changes as a senior engineer would review a PR.

Check for:
1. Code clarity and readability
2. Naming conventions consistency
3. Single responsibility violations
4. Missing error handling
5. Test coverage gaps
6. Documentation needs

Use the format: [file:line] comment (must-fix | suggestion | nit)
  • • Three levels of feedback:must-fix (blocks the merge), suggestion (recommended improvement), nit (aesthetic nitpick). This mirrors how real reviews work
  • • Single responsibility:Claude identifies roles that do too much and suggests how to extract responsibilities
  • • Test coverage gaps:It identifies code paths that have no tests and suggests which tests to write
Practical Tip

💡Practical Tip

The best time to run Code Review andbefore opening the PR. Fix the must-fixes and consider the suggestions. When the human reviewer looks, the PR is already clean and the human review can focus on design and architectural decisions, which is where the human value really lies.

Add team context: "Our team follows Airbnb style guide and uses domain-driven design. Review with these conventions in mind."

🛤️ Refactor Guardrails (Safe Refactoring)

Refactoring is one of the most dangerous tasks in development. You change the structure without changing the behavior, but any silent error can break things in production. The Refactor Guardrails prompt ensures that Claude doessecure refactoring with built-in verification.

Main Concept

🎯Main Concept

The Guardrails Refactor prompt has a structure that prevents regressions during refactoring:

I want to refactor [describe what].

Before refactoring:
1. List all current behaviors that MUST be preserved
2. Identify all callers/consumers of this code
3. Note any implicit contracts or side effects

Then refactor with these guardrails:
- Zero behavior change (same inputs → same outputs)
- Run existing tests after each step
- Flag any test that needs updating and why
  • • Preserved behaviors:Before touching the code, Claude lists everything the code currently does. This creates an explicit "contract"
  • • Callers/consumers:Who uses this code? Changing the signature of a function can break 20 other files if you don't map the dependencies
  • • Implied contracts:Side effects, execution order, state mutations. Claude identifies behaviors that are not in the signature but that other codes depend on
  • • Tests at every step:Incremental refactoring with continuous verification. If a test breaks, you know exactly what change it caused
Practical Tip

💡Practical Tip

Use Refactor Guardrails especially forlegacy code and code without tests. In that case, add: "This code has no tests. Before refactoring, write characterization tests that capture current behavior. Then refactor." Claude creates the tests first and then refactors safely.

Never refactor and add features at the same time. These are two distinct operations. First refactor (without changing behavior), then add the feature to the already clean code.

🔄 Complete Quality Pipeline

Now that you know each type of audit individually, let's put together thecomplete quality pipeline. This is the workflow that professional teams use with Claude Code in 2026 to ensure that all code that reaches production has gone through multiple layers of verification.

Main Concept

🎯Main Concept

The complete Quality Pipeline follows 5 sequential steps. Each step uses a different prompt and focuses on a specific dimension:

  • • Step 1 - Code Review:Readability, conventions, structure. Fix before auditing functionality
  • • Step 2 - Security Audit:OWASP Top 10, vulnerabilities, data exposure. Correct all CRITICALs
  • • Step 3 - Performance Audit:N+1, memory leaks, bundle size. Optimize significant bottlenecks
  • • Step 4 - Brutal General Audit:Edge cases, crash scenarios, everything that specific audits didn't catch
  • • Step 5 - Final verification:"Verify that all CRITICAL and HIGH issues from previous audits have been resolved. List any remaining concerns."

Efficiency tip:You don't need to run the entire pipeline on every code. For hotfixes, use only Security + Brutal Audit. For visual features, use Code Review + Performance. Reserve the entire pipeline for critical features and releases.

Practical Tip

💡Practical Tip

Document pipeline results in yourCLAUDE.md. Add a "Quality Standards" section with the prompts you use. When Claude reads this at the beginning of each session, he already applies the standards automatically during development, reducing findings in audits.

In teams, standardize the pipeline as part of the Definition of Done. No PR is approved without at least Security Audit + Code Review run with Claude Code.

Practical Exercise

Run Brutal Audit in your own code and fix issues

Take a real module from your project (or use an open source project) and apply the quality pipeline:

  2. 2. Rotate theFull Brutal Auditwith structured output (severity + category + file/line + fix)

  5. 5. Run the final check to confirm that the CRITICALs have been resolved
