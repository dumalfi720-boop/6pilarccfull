1

🔍 95% Confidence (Ask Clarifying Questions)

This is the most important prompt of the entire trail. It turns any vague task into a precise task. Instead of letting Claude guess what you want, you force him toask before acting. The result? Less rework, less wrong code, less frustration.

Main Concept

🎯Main Concept

The "95% Confidence" prompt is elegantly simple but brutally effective. You say to Claude:"Ask me clarifying questions, one at a time, until you are 95% confident that you can complete the task successfully."

Ask me clarifying questions one at a time until you're 95% confident you can complete the task successfully.
  • • Prevents blind-spot coding:Claude doesn't assume anything. It asks about edge cases, unmentioned requirements, integrations and design conventions
  • • One question at a time:This is crucial. If you don't specify "one at a time", Claude spits out 15 questions at once and you ignore most of them.
  • • 95% is not 100%:The number 95 is intentional. 100% would be impossible and would stop the process. 95% margin for reasonable uncertainty
  • • Use for everything:New features, migrations, refactoring, complex configurations. Any task that is not trivial deserves this prompt
Practical Tip

💡Practical Tip

Use 95% Confidence asfirst prompt of any complex session. Open Claude Code, describe the task in one sentence, and add the prompt. Answer each question honestly. When Claude says "I'm confident", you know the result will be much better than if you had gone straight.

Advanced tip: you can combine it with context. Example: "I want to implement JWT authentication in this project. Ask me clarifying questions one at a time until you're 95% confident you can complete the task successfully."

2

📋 Plan Mode Blueprint (Think Before Building)

The second Daily Driver is the prompt that forces Claude tothink before coding. Instead of jumping straight into implementation, it first identifies all affected files, plans the step-by-step approach, and flags risks. You approve the plan before any code is written.

Main Concept

🎯Main Concept

The Plan Mode Blueprint follows a clear structure of 4 mandatory steps before touching code:

I want to add [feature].

Enter plan mode. Before writing any code:
1. Identify all files that need to change
2. Outline the approach step by step
3. Flag tradeoffs or risks
4. Wait for my approval
  • • Impact maps:Before any change, you know exactly which files will be affected and can assess whether the scope is correct
  • • Signals risks:Claude warns you about breaking changes, circular dependencies, performance issues and other pitfalls before you fall into them
  • • Explicit approval:"Wait for my approval" ensures you have the last word. Claude doesn't start editing anything until you say "go"
Practical Tip

💡Practical Tip

Plan Mode is especially useful for features that play multiple files. If the change is in a single flat file, you can go straight. But if it involves models, controllers, views, tests and migrations,always use Plan Mode.

After reading the plan, you can ask for adjustments: "The plan is good, but add validation in step 3" or "Remove step 4, I don't need that right now." Claude adjusts the plan and awaits new approval.

3

🐛 Structured Bug Report (Diagnosis Before Fix)

When something breaks, the natural tendency is to ask "fix it." But without structured context, Claude kicks. The Structured Bug Report forces adiagnosis before patch, resulting in fixes that address the root cause rather than masking symptoms.

Main Concept

🎯Main Concept

The Structured Bug Report template has a structure that guides both you and Claude:

When I do [action], I get [error].

Expected behavior: [...]
Current behavior: [...]

Here is the stack trace:
[paste]

Investigate the root cause before attempting a fix.
  • • Action + Error:Describe exactly what you did and what happened. "I clicked the save button and error 500 appeared" is better than "it's giving an error"
  • • Expected vs Actual:This distinction helps Claude understand the nature of the problem. Sometimes the code is "working" but returning wrong data
  • • Stacktrace:Always include. Claude reads stack traces with absurd precision and identifies the exact line of the problem
  • • "Investigate root cause first":This last line is the most important. Without it, Claude may go straight to a superficial patch
Practical Tip

💡Practical Tip

Save this template as a snippet in your editor or create an alias in the terminal. You will use it so much that it needs to be instinctive.Never say "it's breaking, fix it" again. The time invested in structuring the bug report pays off 10x in the quality of the fix.

Bonus: after Claude diagnoses, ask him to explain the root cause before applying the fix. This ensures that you understand what happened and can prevent it in the future.

═══════════════════════════ ════════════════════════════ TOPIC 4: Brutal Audit ═══════════════════════════ ════════════════════════════
4

🔬 Brutal Audit (Find What You Missed)

Brutal Audit is the prompt you useafter building something. He asks Claude to be brutally honest about edge cases, security vulnerabilities, performance bottlenecks, crash scenarios, and anything a senior engineer would flag in a code review.

Main Concept

🎯Main Concept

Brutal Audit covers 5 critical dimensions of quality:

I just built [X].

Audit this for:
1. Edge cases
2. Security vulnerabilities
3. Performance bottlenecks
4. Crash scenarios
5. Anything a senior engineer would flag

Be brutally honest.
  • • Edge cases:Empty lists, null values, unicode, concurrency, timezone, integer limits. Claude finds the scenarios you didn't even think of
  • • Security:SQL injection, XSS, CSRF, data exposure, incorrect permissions. It checks against the most common vulnerabilities
  • • "Be brutally honest":This phrase is essential. Without it, Claude tends to be polite and skip over minor problems. With her, he spares nothing
Practical Tip

💡Practical Tip

Knife of Brutal Audit onemandatory habit. After each significant feature, run the audit. Don't wait until code review or QA finds bugs. The cost of running this prompt is cents. The cost of a bug in production can be enormous.

Tip: after receiving the audit, ask Claude to correct critical items automatically. He already knows exactly where the problems are.

═══════════════════════════ ════════════════════════════ TOPIC 5: Teach Me What You Did ═══════════════════════════ ════════════════════════════
5

🎓 Teach Me What You Did (Learn From the AI)

The fifth Daily Driver and what transforms the Claude Code from a tool intoskill amplifier. After Claude makes a correction, a refactoring or an implementation, you ask him to teach you what he did, why he did it and what you should observe next time.

Main Concept

🎯Main Concept

Teach Me has 4 learning dimensions:

I just watched you [from X].

Now teach me:
1. The root cause or core concept
2. Why this approach was chosen
3. What would break if we didn't fix it
4. What to watch for next time

Explain it so I could do it myself.
  • • Root cause:Not just what was done, but why the problem existed in the first place. This builds deep understanding
  • • Why this approach:Were there alternatives? Why was this chosen? What trade-offs are there?
  • • "So I could do it myself":This final sentence ensures that the explanation is practical, not theoretical. Claude adapts the level so you can replicate
Practical Tip

💡Practical Tip

Use Teach Me especially when Claude does something youdidn't fully understand. If he used a complex regex, a design pattern you don't know, or an obscure configuration, it's the perfect time for this prompt.

Over time, you will notice that you need Teach Me less and less for certain types of tasks. This means the prompt is working: you are learning and retaining the knowledge.

6

🔄 Combining the 5 in Everyday Life

The 5 Daily Drivers are not isolated prompts. They form acomplete work system. When combined in the right sequence, they cover the entire development cycle: understanding, planning, execution, validation and learning.

Main Concept

🎯Main Concept

The complete workflow of the 5 Daily Drivers follows this sequence for any non-trivial task:

  • • Step 1 - 95% Confidence:Start every complex task with clarifying questions. This prevents 80% of future problems
  • • Step 2 - Plan Mode:With the context clear, ask for the implementation plan. Review and approve any code beforehand
  • • Step 3 - Build:Execute the approved plan (we will look at specific building prompts in module 4.3)
  • • Step 4 - Brutal Audit:Audit the result. Fix critical issues
  • • Step 5 - Teach Me:Learn from the process. Especially useful when there were bugs or interesting design decisions

What about when there are bugs during the build?Use the Structured Bug Report to diagnose and fix, then continue with the normal flow.

Practical Tip

💡Practical Tip

You don't need to use all 5 in every task. For a simple bug, just use the Structured Bug Report. For a quick feature, use 95% Confidence + Plan Mode. Reserve the full cycle for significant work: large features, migrations, larger refactorings.

Rule of thumb:If the task will take more than 30 minutes, use the full cycle. Investing 5 minutes in planning saves 30 in rework.
