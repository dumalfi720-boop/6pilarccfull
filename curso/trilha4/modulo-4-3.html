TOPIC 1: Feature Blueprint
1

📐 Feature Blueprint (Plan Mode Approach)

The Feature Blueprint and the evolution of Plan Mode tospecific features. While the generic Plan Mode asks for a general plan, the Blueprint goes deeper: it identifies all the files that need to change, details the step-by-step approach, and maps feature-specific risks.

🎯Main Concept

I want to add [feature].

Enter plan mode:
1. Identify affected files
2. Outline approach
3. Flag risks
4. Wait for approval
  • • Affected files:Claude navigates the codebase and lists exactly which files need to be created, modified, or deleted. This avoids surprises in the middle of the build
  • • Detailed approach:It's not "add authentication". And "1. Create auth middleware in src/middleware/auth.ts, 2. Add user schema in prisma/schema.prisma, 3. Create POST route /auth/login..." - each step is concrete
  • • Risks flagged:"This feature requires changes to the users table that may affect existing queries" - this type of warning prevents disasters

💡Practical Tip

Before approving the blueprint, ask questions:"What if the user is logged out?", "How does this affect mobile?", "Do you need migration?". The more you question the plan, the better it gets. The cost of adjusting a plan is zero. The cost of redoing code is high.

TOPIC 2: Build With Tests
2

🧪 Build With Tests (TDD Prompt)

Build With Tests and the prompt it implementsTest-Driven Development with Claude Code. Instead of building the feature and then writing tests (which almost never happens), you force Claude to write the test first, implement it, run it, and then move on to the next piece.

🎯Main Concept

Build [feature].

For each piece:
1. Write test first
2. Write implementation
3. Run tests
4. Move to next piece

Do not batch test.
  • • Test first:Claude writes the test that defines the expected behavior. Then write the code that makes the test pass. This ensures that every piece works before moving forward.
  • • Actual execution:Claude runs the tests on the terminal. If it fails, correct it before continuing. You see the red-green cycle happening in real time
  • • "Do not batch tests":Without this instruction, Claude tends to write all the tests at once and then the entire implementation. This negates the benefit of TDD

💡Practical Tip

Make sure your project already has a testing framework configured (Jest, Vitest, pytest, etc.) before using this prompt. Claude needs poweractually run the tests. If there is no test runner, ask first to configure one.

TOPIC 3: Incremental Building
3

🧱 Incremental Building (Step-by-Step)

Not every feature needs formal TDD. Incremental Building is the versionstep-by-step construction pragmatics. Claude builds a piece, checks that it works, and then moves on to the next one. No automated tests, but validation at every step.

🎯Main Concept

Incremental Building works with a prompt that forces pauses between steps:

Build [feature] incrementally.

After each step:
1. Show what was built
2. Check it works
3. Wait for my OK before continuing

Start with the smallest working version.
  • • Smallest working version:Start with the minimum viable. An endpoint that returns hello world. A component that renders a div. Then it evolves incrementally
  • • Manual checkpoints:At each step you validate visually or with a manual test. Only after your OK does Claude continue. This prevents it from building 500 lines of code that don't compile
  • • Ideal for UI:Building interfaces incrementally allows you to see the visual outcome at each step and ask for adjustments before adding more complexity

💡Practical Tip

Combine Incremental Building withgit commits at each checkpoint. After each "OK", ask Claude to commit. This way, if something goes wrong in a future step, you can go back to the last stable point without losing everything.

TOPIC 4: Component Building
4

🎨 Component Building (UI Component Prompt)

Building UI components requires a specific type of prompt. The Component Building prompt definesprops, states, variants and accessibilityin a structured way, guaranteeing complete and reusable components from the first version.

🎯Main Concept

Build a [component name] component.

Requirements:
- Props: [list expected props]
- States: [default, hover, active, disabled, loading]
- Variants: [primary, secondary, ghost]
- Accessibility: keyboard nav, aria labels, screen reader

Follow existing component patterns in the codebase.
  • • Explicit proposals:Listing the props prevents Claude from inventing interfaces that don't make sense for his design system
  • • All states:Hover, active, disabled, loading. Without this, Claude only builds the default state and you discover the others in QA
  • • "Follow existing patterns":Claude reads existing components and replicates the same style, naming conventions and file structure

💡Practical Tip

If you use Storybook or similar, add to the prompt:"Also create a Storybook story showing all variants and states."Claude generates the component and visual documentation at once.

TOPIC 5: API Endpoint Building
5

🔌 API Endpoint Building (Backend Prompt)

API endpoints have specific requirements: input validation, error handling, authorization, pagination. The API Endpoint prompt ensures thatnone of these aspects are forgotten, producing production-ready endpoints from scratch.

🎯Main Concept

Build a [METHOD] /api/[resource] endpoint.

Requirements:
- Input validation with error messages
- Proper HTTP status codes
- Error handling (try/catch, custom errors)
- Authentication/authorization check
- Rate limiting considerations

Follow existing API patterns in this codebase.
  • • Validation with messages:It's not enough to validate. The user needs to know what went wrong. "email is required" is better than "validation error"
  • • Correct status codes:201 for creation, 404 for not found, 422 for validation. Claude knows all HTTP status codes and uses them correctly when instructed
  • • Auth/authz:Specifying that the endpoint needs authentication avoids the classic error of public endpoints that should be protected

💡Practical Tip

For full RESTful APIs, build a full CRUD endpoint at once with the prompt:"Build full CRUD for [resource]: GET list (with pagination), GET by id, POST, PUT, DELETE. Follow REST conventions and existing patterns."Claude generates all endpoints consistent with each other.

TOPIC 6: Full-stack Feature Workflow
6

🔗 Full-Stack Feature Workflow

Most real-world and full-stack features: database + backend + frontend. The complete workflow combines all the prompts from this module into oneend-to-end sequencethat produces complete features with production quality.

🎯Main Concept

The full-stack workflow follows this sequence:

  • • Step 1 - Feature Blueprint:Plan the complete feature: schema, API, components, tests
  • • Step 2 - Database/Schema:Create or modify the database schema. Migrations if necessary
  • • Step 3 - API Endpoints:Build endpoints with validation, auth and error handling
  • • Step 4 - UI Components:Build the components that consume the API
  • • Step 5 - Integration:Connect everything and test end-to-end flow
  • • Step 6 - Brutal Audit:Audit the complete feature before considering it ready

💡Practical Tip

For large features,use separate sessions for each layer(database, API, UI). This keeps the context clean and prevents Claude from mixing backend and frontend concerns. Reference the files created in the previous steps explicitly in each new session.
