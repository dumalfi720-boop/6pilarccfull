MODULE 2.4

📜 Modular Rules (.claude/rules/)

Discover how to use the .claude/rules/ directory to create modular rules organized by file type and context. The evolution of the monolithic CLAUDE.md.

📜 What are Modular Rules

Modular rules are individual files within the directory.claude/rules/which contains specific instructions for Claude. Instead of a single giant CLAUDE.md, you candivide the rules into thematic files.

🎯Main Concept

  • •.claude/rules/ directory:Each .md file in this directory is loaded as an additional rule
  • •Modularity:One rule per file facilitates organization, review and maintenance
  • •Automatic charging:All files in the directory are automatically read when logging in
  • •Complements CLAUDE.md:Works together with CLAUDE.md, does not replace

💡Practical Tip

Think of .claude/rules/ as a 'configuration directory' for Claude. Just as .eslintrc, .prettierrc define rules for tools, .claude/rules/ defines rules for Claude.

2

🔄 Difference between CLAUDE.md and rules/

CLAUDE.md and rules/ coexist, but they servedifferent purposes. Understanding when to use each one is key to an efficient organization.

🎯Main Concept

  • •CLAUDE.md:Project overview: stack, commands, general conventions. The 'executive summary'
  • •rules/:Detailed and specific rules: by file type, by context, by code area
  • •Analogy:CLAUDE.md is the employee manual. rules/ are the detailed operating procedures
  • •Practical rule:If it fits in 3 lines, put it in CLAUDE.md. If you need more details, create a file in rules/

💡Practical Tip

Use CLAUDE.md for what everyone needs to know in 30 seconds. Use rules/ for details that only matter in specific contexts. Do not duplicate information between the two.

3

📝 Creating your First Rule File

Creating a rule file is simple: just create a file.mdinside.claude/rules/. The file name describes the rule theme.

🎯Main Concept

  • •Structure:Create the .claude/rules/ directory and add .md files inside
  • •Nomenclature:Use descriptive names: testing.md, api-patterns.md, frontend-rules.md
  • •Format:Simple Markdown with bullets, headers and code examples
  • •Versioning:Add .claude/rules/ to git to share with the team

💡Practical Tip

Start with a single rule file for the area that bothers you most. If Claude always fails tests, create .claude/rules/testing.md with your testing rules. Then expand.

4

📄 Rules by File Type

One of the most powerful applications of rules/ is to createrules by file type. Rules for .test.ts files, rules for .py, rules for .css. Each file type has its own conventions.

🎯Main Concept

  • •testing.md:Testing conventions: framework, patterns, mocks, assertions, minimum coverage
  • •components.md:Rules for React components: props typing, hooks usage, styling approach
  • •api-routes.md:API patterns: validation, error responses, authentication, pagination
  • •styles.md:CSS/Tailwind conventions: utility classes, custom themes, responsive breakpoints

💡Practical Tip

The real power comes when you have specific rules for testing. Create .claude/rules/testing.md saying: 'Use describe/it pattern, mock with vi.fn(), assertions with expect().toBe(), never use any in test types'. Claude will generate tests that fit perfectly.

5

🛠 Rules by Context

In addition to file type, you can create rules bywork context: frontend, backend, infrastructure, CI/CD. Each context has its own needs and restrictions.

🎯Main Concept

  • •frontend.md:Rules for frontend code: components, hooks, state management, routing
  • •backend.md:Backend rules: API design, database queries, error handling, logging
  • •infra.md:Infrastructure rules: Docker, CI/CD, deploy, environment variables
  • •security.md:Security rules: input validation, auth patterns, secret management

💡Practical Tip

In a monorepo, rules per context are essential. The frontend can use React with Tailwind while the backend uses Express with SQL. Each context deserves its rules file to prevent Claude from mixing conventions.

6

📚 Good Rule Organization Practices

The organization of.claude/rules/It can become complex if you don't followgood practices. Keep it simple, keep it clear, keep it updated.

🎯Main Concept

  • •Few large files > many small files:5-10 well-organized files and better than 50 micro-files
  • •Descriptive names:testing.md is better than rules-01.md. The name should tell the content
  • •Periodic review:Every sprint, review whether the rules still make sense
  • •Git and PR review:Treat changes to rules/ as code changes. Review on PRs

💡Practical Tip

Create a README.md inside .claude/rules/ listing the purpose of each file. This helps new team members understand the organization and know where to add new rules.

Practical Exercise

Exercise: Create 3 Modular Rules Files

Estimated time: 15-20 minutes

1

Create the directory

In your project, create the .claude/rules/ directory if it does not already exist.

2

Create test rule

Create .claude/rules/testing.md with testing conventions: framework, patterns, assertions, coverage.

3

Create API rule

Create .claude/rules/api-patterns.md with API patterns: validation, error responses, auth.

4

Create style rule

Create .claude/rules/code-style.md with style conventions that are not in CLAUDE.md.

5

Test

Open Claude Code and ask to create an API test and route. Check whether the rules are being followed.
