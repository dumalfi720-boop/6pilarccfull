TOPIC 1: Project Overview
1

📝 Project Overview section

The first section of CLAUDE.md is the most important: theProject Overview. In 2-3 sentences, you explain what the project does, what the domain is and what the main stack is. Claude uses this as an anchor for all subsequent decisions.

🎯Main Concept

Project Overview answers three questions:What is it?, For whom? e With what technology?. Keep it short and to the point.

## Project Overview
This is SaaSify, a B2B subscription management platform.
Built with Next.js 14 (App Router), TypeScript, and Supabase.
Target users: SaaS companies managing recurring billing.
  • •Be specific:"B2B subscription platform" is better than "web application"
  • •Include the main stack:Claude adjusts his suggestions based on the declared stack
  • •Maximum 3 sentences:It's not README. And quick context

💡Practical Tip

Write the Project Overview as if you were answering the question "What are you building?" to a senior colleague in one sentence. If you need more than 3 sentences, you are including too much detail.

TOPIC 2: Tech Stack and Commands
2

⚙️ Tech Stack and Commands Section

The section ofTech Stack and Commandsand where you declare the project technologies and the commands that Claude should use. This is crucial because Claude frequently needs to run commands and needs to know which package manager and which scripts to use.

🎯Main Concept

List your stack as bullet points and your commands as key-value pairs. Claude uses this to know which tool to use in each situation.

## Tech Stack
- Language: TypeScript (strict mode)
- Framework: Next.js 14 with App Router
- Database: Supabase (PostgreSQL)
- Styling: Tailwind CSS + shadcn/ui
- Testing: Vitest + Playwright
- Package Manager: pnpm

##Commands
- Dev: pnpm dev
- Build: pnpm build
- Test: pnpm test
- E2E: pnpm test:e2e
- Lint: pnpm lint
- Type check: npx tsc --noEmit
  • •Package Manager explicitly:Without this, Claude can use npm when you use pnpm
  • •All important commands:Dev, build, test, lint, type check. Claude uses these commands frequently
  • •Specific versions where relevant:"Next.js 14 with App Router" is much more useful than just "Next.js"

💡Practical Tip

The most common mistake is forgetting the package manager. If you use pnpm and don't declare it, Claude will runnpm installand create an unwanted package-lock.json in your project. Always state it explicitly.

TOPIC 3: Code Conventions
3

📐 Code Conventions Section

The section ofCode Conventionsdefines how the code should be written. This is where you prevent Claude from generating code that "works but isn't the right way" for your project.

🎯Main Concept

Document only those conventions that arespecific to your project. You don't need to say "use camelCase in JavaScript". Focus on what is unique.

## Code Conventions
- Use Server Components by default, Client Components only when needed
- Named exports for all components (never default export)
- File naming: kebab-case for files, PascalCase for components
- Place tests next to source files as *.test.ts
- Use Zod for all input validation
- Prefer composition over inheritance
- All API responses follow { data, error, meta } pattern
  • •Exports:Named vs default is one of the biggest sources of inconsistency. Explicitly state
  • •Naming:kebab-case, camelCase, PascalCase for each context
  • •Patterns:API response patterns, error handling, validation

💡Practical Tip

Review the last 5 PRs you made style corrections. Every correction you made is a convention that should be on CLAUDE.md. If you corrected "use named export" 3 times, add this rule.

TOPIC 4: Important Patterns
4

🔗 Important Patterns Section

The section ofImportant PatternsDocuments the project’s architectural standards. Error handling, state management, authentication, API calls. These standards are what separate code that "works" from code that "fits" the project.

🎯Main Concept

Architectural patterns are decisions that affect multiple files and functionalities. Claude needs to know them to generate consistent code.

## Important Patterns
- Error handling: Use Result<T, E> pattern, never throw in business logic
- State management: Zustand for client state, React Query for server state
- API calls: Always through src/lib/api.ts, never fetch directly
- Authentication: Supabase Auth with JWT, middleware checks in middleware.ts
- Database queries: Always through repository pattern in src/repositories/

💡Practical Tip

If you have a specific error handling pattern, write a mini-example in CLAUDE.md. Claude learns much better from concrete examples than from abstract descriptions. Show the "bad before" and the "right after".

TOPIC 5: Things To Avoid
5

🚫 Things To Avoid Section

The sectionThings To AvoidIt is as powerful as positive rules. Tell Claude whatNOT to doprevents common mistakes before they happen. This section works like automatic guardrails.

🎯Main Concept

Negative rules are easier to follow than positive rules. "Never use any" is clearer than "always use proper types". Use direct and imperative language.

## Things To Avoid
- Never use "any" type — use "unknown" and narrow
- Don't use the Pages Router — App Router only
- Never commit .env files
- Don't install new dependencies without discussing first
- Never use console.log in production code — use the logger
- Don't create files outside the src/ directory
  • •Use "Never" and "Don't":Strong, unambiguous language works best with LLMs
  • •Briefly explain the reason:"Never use any — use unknown and narrow" is better than just "Never use any"

💡Practical Tip

Every bug you found because Claude did something wrong is a candidate for Things To Avoid. Keep a mental log and update this section regularly. After 2 weeks of use, this list becomes pure gold.
