TOPIC 1: Purpose Section
1

🎯 Purpose Section (Objective in One Sentence)

The Purpose section and thefirst line of defense against ambiguity. It is a single sentence that describes the final result that the skill should produce. Without a clear Purpose, Claude can interpret the skill in different ways with each invocation.

🎯Main Concept

Purpose must bea single result-oriented sentence. It doesn't describe the process, it describes what the user receives at the end. Examples:

  • • Good:"Convert a design screenshot into a pixel-perfect responsive web page using Tailwind CSS"
  • • Good:"Perform code review at senior PR level with severity classification"
  • • Bad:"Help with code" (very vague, without measurable results)
  • • Bad:"Read files and analyze and then generate a report and send" (multiple mixed results)

💡Practical Tip

Use the "one sentence" test: if you can't describe the result in one sentence, the skill is too complex. Split into two or more smaller skills. Focused skills are more reusable and produce better results.

TOPIC 2: Inputs Required Section
2

📥 Inputs Required section

The Inputs Required section defineswhat the user needs to providefor the skill to work. Without clear inputs, Claude may ask for information during execution or assume inappropriate defaults.

🎯Main Concept

Inputs must be listed explicitly, with type and description:

## Inputs Required
- Screenshot or URL of the design (image or link)
- Target framework (React, Vue, pure HTML)
- Desired breakpoints (mobile, tablet, desktop)
- Color palette (if different from screenshot)
  • • Be specific:"Image file" is better than "visual reference". Claude needs to know exactly what to expect
  • • Indicate optionality:Mark optional inputs with "(optional)" so Claude knows which ones to skip
  • • Include defaults:If an input has a default value, specify: "Target Framework (default: HTML with Tailwind)"

💡Practical Tip

The fewer mandatory inputs, the easier to use the skill. Set smart defaults for everything you can. The user only needs to provide what is unique to each invocation. The rest should have reasonable default values.

TOPIC 3: Steps Section
3

📝 Steps Section (Detailed Steps)

The Steps section is theskill heart. Here you define each step that Claude must follow, in order, with instructions specific enough to produce consistent results. Vague steps generate vague outputs.

🎯Main Concept

Each step must have a clear title and specific instructions:

## Steps
### Step 1: Analyze the Design
Examine the screenshot and identify:
- Grid system (columns, gaps)
- Spacing (padding, margin)
- Exact colors (extract hex values)
- Typography (font-family, sizes, weights)
### Step 2: Plan Semantic HTML
Before writing code, create a structure outline:
- Identify reusable components
- Define heading tag hierarchy
- Map interactive elements
  • • Be specific:"Analyze colors" is vague. "Extract hex values ​​from each color visible in the screenshot" is specific and actionable
  • • Include WHY:Adding the reason behind each step helps Claude make better decisions when he encounters ambiguity
  • • Order logically:Steps should follow a natural progression. Analysis before implementation, implementation before testing

💡Practical Tip

The golden rule for steps:If you were to train a junior to do this task, what instructions would you give?This level of detail is ideal for a skill. Claude is extraordinarily capable, but specific instructions produce specific results.

TOPIC 4: Quality Checks Section
4

✅ Quality Checks Section

Quality Checks are theself-check mechanismof the skill. Without them, Claude delivers the result and moves on. With them, Claude checks each criterion before considering the task complete. And the difference between "done" and "done right".

🎯Main Concept

Quality Checks must be objectively verifiable:

## Quality Checks
- [ ] Layout matches the original screenshot
- [ ] Color hex values ​​are exact
- [ ] Typography and true to design
- [ ] Responsive on mobile, tablet and desktop
- [ ] Hover and focus states included
- [ ] No console errors
  • • Objectives, not subjective:"Clean code" is subjective. "Functions with less than 50 lines" are objective and verifiable
  • • Use checkbox syntax:The format- [ ]signals to Claude that each item needs to be checked individually
  • • Cover edge cases:Include checks for scenarios that are often forgotten: error states, loading states, empty fields

💡Practical Tip

Start with 4-6 essential quality checks. Skills with many checks (10+) can make execution slow and expensive in tokens. Focus on the criteria that really differentiate an “ok” result from an “excellent” result. If necessary, group related checks together.

TOPIC 5: Output Section
5

📤 Output Section (Expected Delivery)

The Output section describesexactly what Claude should deliverwhen finishing the skill. Without this, Claude may deliver the result in an unexpected format: a file when you expected text in the console, or vice versa.

🎯Main Concept

The Output must specify format, structure and delivery location:

## Output
Production-ready HTML/CSS files in the project directory:
- index.html with complete semantic structure
- Tailwind inline classes (no custom CSS)
- README with preview instructions
  • • Explicit format:Specify whether the output is file, console text, table, JSON, CSV, etc.
  • • Location:Indicate where the files should be created (current directory, specific subfolder, etc.)
  • • Minimum quality:"Production-ready" vs "Prototype" vs "Draft" defines the level of polish expected

💡Practical Tip

Include an example of the expected output when possible. If the skill generates a report, show the structure of the report. If it generates code, show the expected file structure. Concrete examples eliminate ambiguity more than any textual description.

📋 Complete Commented Template

Here is thecomplete and official templateto create professional skills. Copy this template, fill it in with your specific workflow and save it in.claude/commands/.

🎯Main Concept

# Skill: [Descriptive Name]
## Purpose
ONE sentence describing the end result
[Verb + object + qualifier]
## Inputs Required
What the user needs to provide
- [Mandatory input 1 (type/format)]
- [Mandatory input 2 (type/format)]
- [Optional input (optional, default: X)]
## Steps
Steps in logical order
### Step 1: [Clear Action]
[Specific instruction with sufficient details]
[Include WHY when relevant]
### Step 2: [Clear Action]
[Specific instruction]
### Step 3: [Clear Action]
[Specific instruction]
## Quality Checks
Objective and verifiable criteria
- [ ] [Verifiable criterion 1]
- [ ] [Verifiable criterion 2]
- [ ] [Verifiable criterion 3]
## Output
Clear description of the deliverable
[Format + location + quality level]

💡Practical Tip

Six rules for excellent skills:1)Be specific, vague steps generate vague output.2)Include checklists for self-checking.3)Start with 25 test invocations before scaling up.4)Add the WHY behind the steps.5)Version your skills in git.6)Share in the team repository.

Practical Exercise

🏋️

Exercise: Build Complete Skill

Estimated time: 20-25 minutes

1

Choose a repetitive workflow

Identify something you do frequently: generate tests, document functions, create boilerplate, etc.

2

Write Purpose and Inputs

Define the result in a sentence and list all necessary inputs with types and defaults.

3

Detail Steps with specific instructions

Write 3-5 steps with clear instructions. Include the reason for each step when relevant.

4

Add Quality Checks and Output

Create 4-6 objective verification criteria and describe the final deliverable with format and location.

5

Test 3 times and iterate

Invoke the skill 3 times with different inputs. Adjust steps and checks based on results.

☐ Purpose in a clear sentence
☐ Inputs with types and defaults
☐ Specific and ordered steps
☐ Verifiable Quality Checks
